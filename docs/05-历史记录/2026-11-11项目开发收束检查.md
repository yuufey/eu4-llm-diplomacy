# 2026-11-11项目开发收束检查

本页保留2026-11-11的检查结论。2026-11-12用户调整执行顺序，先补完既定信息导出条目，再进行整体使用验证；当前开发依据见[开发计划](../信息导出与订阅开发计划.md)。

用户随后将战报范围收束为胜负、双方损失等战略必要信息，原生Line1、完整弹窗原文及控件还原归后续扩展。下方对这些内容的历史缺项描述按当前计划解释。

本次由主代理独立检查，依据README最终目标、当前范围审查、开发计划、近期交接和355至362批收据。检查期间只阅读现有材料并更新文档。结论涉及当前证据能够支持的交付状态，未重新运行游戏或整套测试。

## 目标与当前距离

项目最终目标是让LLM负责指定非玩家国家的外交决策，游戏原生AI继续负责军事、经济等系统，并支持玩家文字谈判。信息模块的交付价值在于让LLM理解局势、比较外交选择、及时处理提议，以及在执行后根据结果调整判断。[项目目标](../../Readme.md)

已经有可复用的宏观信息基础。355批两份报告的78个所选字段中77项已知、1项不适用，情境报告耗时约32.97秒。356批交付两条法国修正自然到期事件、26条提议和一条法国参战记录。360批正式v61部署后，普通八字段查询全部已知，耗时9.609秒。字段数量和查询时间来自不同报告，不能直接横向比较，也不能换算为项目完成百分比。[355收据](../../work/runtime/information-core-repair-20261110-355-001/summary.json) [356收据](../../work/runtime/information-macro-expiry-live-20261110-356-001/summary.json) [360收据](../../work/runtime/information-rival-release-20261110-360-001/summary.json)

这些材料证明了查询与部分事件交付能力。近期材料尚未提供一次真实LLM消费报告、提出外交选择、调用既有行动预览、处理执行结果的完整演示。C03已有战略目标和约束输入，但该输入本身不证明LLM决策循环已接通。本次没有穷举整个仓库来断言所有LLM集成都不存在。[输入实现](../../bridge/information/decision_context_inputs.py)

## 存在的偏离

### 局部研究缺少完成边界

战报和宏观即时通知都是已有明确需求，研究这些内容具有依据。开发过程中持续追加局部来源和细节研究，使既定信息条目的完成边界模糊。当前执行顺序为先补完既定信息导出条目及事件，再开展整体使用验证。每项研究围绕明确的战略用途和目标字段安排，达到完成条件后继续下一项。

富瓦战报已经包含双方兵力、损失、胜负和30段所选可读文本，仍有原生Line1和战争编号缺口。362批修正了原生全歼时撤退状态的适用性。后续按B01–B04的明确字段补齐剩余内容，继承已通过的验收，并为原文研究限定目标范围。[362收据](../../work/runtime/information-battle-core-20261110-362-001/summary.json)

独立撤回来源仍影响提议生命周期，值得继续解决。不过361批找到的是共享清理路径，尚不能标记撤回原因。后续应先明确它对消费者的影响，例如是否会把已失效提议继续当成待办，再决定需要补何种状态或来源。不能把“所有销毁原因都解释完”直接当作接入条件。[361收据](../../work/runtime/information-proposal-queue-20261110-361-001/summary.json)

### 研发进度衡量偏向内部活动

来源数量、DLL版本、测试数量和批次数量主要衡量实现及验证活动。它们不能回答LLM是否已能比较结盟、开战、参战、援助或议和选择。当前需要把“对一个决策问题缺什么”放回首位，并明确使用现有信息的实际障碍。

`partial`尤其需要分解。某个可读报告缺少原生控件文本，不会自动使已知财政或军力失去决策价值。相反，观察国错误、关键数值单位错误、遗漏必须回应的提议、执行结果无法确认，可能直接阻断决策，应优先修复。

### 复盘规则已经写过，执行仍有反复

11月7日复盘已要求按决策用途开发、继承已有验收、减少共享入口重复演示。随后仍出现重复工具成本和夹具返工。361批REA查询再次触及资源上限。362批首先发生临时目录权限错误，真实记录回放又因缺少catalog、比较层次错误、分页假设错误经历三次失败。360批重复安装同一物理Hook入口导致首版部署失败。这些都有具体原因，可通过复用已工作的入口和集中维护安装所有权减少。[既有复盘](2026-11-07开发范围与验证及委派复盘.md) [360收据](../../work/runtime/information-rival-release-20261110-360-001/summary.json) [362收据](../../work/runtime/information-battle-core-20261110-362-001/summary.json)

362批197个唯一相关测试通过，不能仅凭数量判定测试浪费。真正的问题是验证选择是否由受影响合同驱动，以及是否为每个小改动重建查询、订阅、重开和监控脚本。原生Hook的ABI、回滚、身份和可见性检查仍有直接用途。优化应优先消除夹具重造、重复启动和与改动无关的整套演示。

### 状态文档影响开发判断

README的状态仍以10月中旬为主，无法反映近期信息模块交付。开发计划和剩余缺项页面又混入大量批次历史，读者必须自行辨别哪些“尚待部署”已经被后续部署覆盖。362批已有结果和收据，但交接顶部仍停在361批，说明记录同步本身也存在断点。

后续当前状态只写可用能力、实际阻塞和下一交付，历史过程链接至收据和交接。计划正文不再为每个批次复制整段日志。本次先补当前入口，历史记录整理可以独立进行，避免为了整理材料再次中断交付。

## 调整后的执行顺序

| 优先级 | 下一交付 | 验收依据 |
| --- | --- | --- |
| P0 | 补齐既定宏观战略信息查询条目 | 目标字段通过正常入口导出，业务含义明确，默认输出简洁 |
| P1 | 完成宏观即时通知、独立撤回和完整战报的剩余明确要求 | 按所需内容、捕获、顺序、去重、断档和订阅交付逐项完成 |
| P2 | 修复影响上述交付的整合故障 | 复用现成错误栈和调度、恢复验收，核心查询、报告与订阅能持续使用 |
| P3 | 信息条目与事件补齐后开展LLM整体使用验证 | 完成外交方案比较、行动预览与结果复查，记录输出体积与总耗时 |
| 后续 | 当前决策无实际需要的显示细节、稀有机制和穷尽归因 | 有新场景证明价值后安排 |

以上顺序已按2026-11-12用户要求调整。信息模块先完成既定查询、事件和战报交付，再进行整体使用验证。正式LLM外交循环、谈判和长期记忆属于项目整体里程碑，按相应计划安排。

## 提速的具体做法

1. 每轮只确定一个面向使用者的交付结果，先说明缺少哪项信息会改变哪个外交选择。已有接口能回答时直接复用。
2. LLM先读取国家级摘要和重要事件，涉及具体行动再按需展开。性能同时记录墙钟时间、重复解析、输出体积和模型输入成本。32.97秒报告需先定位主要耗时项，不能据此直接断言游戏卡顿。
3. 关键事件与周期摘要分别调度，执行前重新核对即时合法性。宏观信息以观测日期表达新旧程度，字段是否可用依据具体性质处理。
4. 为来源研究设停止条件。一次有界分析未得到可用于生产的结果时，记录缺口、已有可用信息和下一条具体假设，再与其他交付比较优先级。相同REA初始化已超限时优先使用现有证据和窄范围分析。
5. 复用工作区临时目录、公共入口夹具和分页消费逻辑。为具体回归增加最少必要测试，既有测试通过后以新改动或新故障为继续扩大检查的依据。
6. 自然观察围绕具体事件或已知期限安排，得到目标结果即结束。稀有正例缺失时明确证据不足，避免把长期等待本身当成开发进度。
7. 本次检查不开启子代理。后续委派仍需由主代理确定交付与语义，只有可独立完成且节省总工时的机械工作才适合委派。

无法从现有批次收据可靠还原所有开发、等待和返工工时，因此本次不报告“浪费时间百分比”或预计提速倍数。后续按既定信息条目的完成情况衡量进度，整体使用效果在整合阶段验证。
