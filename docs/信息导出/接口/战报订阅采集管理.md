# 战报订阅采集管理

本文说明 B01、B04 逐场战报订阅从服务配置到 native battle producer 的实际连接。文中的方法名和字段名以当前实现为准；本文不把一次读取到的旧战报当成未来采集能力。

## 先看结论

--battle-ingest-installation 这个 flag 本身只让 LiveBattleIngestor.refresh() 增量读取已安装来源的 raw log，并把记录写入 battle SQLite。它不向 native producer 发送 enable 或 disable，也不注入、推进游戏时间或保存游戏。因此，未启用 capture manager 且当前 producer 为 disabled 时，新订阅只能读取或重放已经在数据库中的记录；它不会因为创建订阅而自动收到未来自然战斗。

只有显式加上 --battle-manage-capture，服务才会为 live battle stream 创建 BattleCaptureManager。B01/B04 所在的 event subscription 被激活后，manager 才会在已经安装且已经绑定的 producer 上取得共享 lease：首个需要战报采集的消费者可以启用一个已绑定且 disabled 的来源，最后一个消费者释放时只关闭本 manager 自己启用的来源。一个外部已经启用的来源只会被借用，最后释放也不会被关闭。

当前实现使用 bridge/information/battles.py 中的 EVENT_TYPE = "battle_observation" 来判断某个 event subscription 是否需要 battle capture。服务比较的是订阅中的 event.types，不能把 native/raw 结束通知的其他标签当作服务 API 名称。

## 启动方式与边界

live 管理需要同一个已核验的 operator installation 同时作为 --operator-session 和 --battle-ingest-installation。下面的路径只是占位符；命令中没有写入当前进程 PID 或当前运行目录。

`--database` 是服务配置与结果数据库；`battle-stream.json` 的 `database` 是战报摄取数据库，两者必须使用不同文件。启用摄取时，服务会在构造摄取器前比较规范化路径，并用文件身份检查已有文件的硬链接等别名；同一文件会使启动失败，已创建的 journal 随即关闭。这样可以避免服务事务占用写锁，导致另一个连接无法摄取。未启用摄取的只读模式不受这项限制。

    python tools/serve_information.py --jsonl --database '.\path\service.sqlite3' --operator-session '.\path\installation.json' --battle-stream '.\path\battle-stream.json' --battle-ingest-installation '.\path\installation.json' --battle-manage-capture

只做数据库刷新和历史读取时，可以省略 --battle-manage-capture：

    python tools/serve_information.py --jsonl --database '.\path\service.sqlite3' --operator-session '.\path\installation.json' --battle-stream '.\path\battle-stream.json' --battle-ingest-installation '.\path\installation.json'

各 flag 的实际作用如下。

| 入口 | 实际作用 | 不代表的能力 |
| --- | --- | --- |
| --battle-stream | 加入显式 opt-in 的本地 battle-record source/SQLite；source 按已绑定 observer 范围提供记录 | 不会单独启用 native producer |
| --battle-ingest-installation | 为已安装的 installation.json 创建 LiveBattleIngestor；在绑定通过时由 _refresh() 调用 refresh() 读取 raw log | 不会发送 native 控制请求，也不证明未来战斗一定会产生新记录 |
| --battle-manage-capture | 为 live stream 创建 BattleCaptureManager，让需要 battle event 的订阅共享 enable/disable lease | 不能用于 recorded、unbound 或非 live stream；不会注入、推进时间或保存 |
| --operator-session | 提供已核验的 observer installation；使用 capture 管理时必须与 ingest path 解析到同一文件 | 不等于 native 的 player_ref |
| --observer | 服务查询和 scope 使用的 observer 国家标签，例如 FRA | 不能作为 native 控制请求的 player_ref |

--battle-ingest-installation 必须和 --battle-stream 一起使用。--battle-manage-capture 还要求两条 installation 路径相同，并要求 battle binding 的 mode 为 live。缺少 binding、binding 不匹配、记录来源为历史/离线来源时，服务不能管理 native producer。

可以用控制桥读取只读状态：

    python tools/control_information_battle_observer.py --installation '.\path\installation.json' --command status

status 只读取并核对 status/binding 文件，不创建 native request。manager 的默认 controller 延迟调用 tools.control_information_battle_observer.run_control；生命周期代码允许的 command 只有 status、enable、disable。服务不会通过该入口注入动作、推进日期或保存游戏。

## 组件和真实接口

生命周期由几个有明确边界的组件组成。

| 组件 | 责任 |
| --- | --- |
| tools/serve_information.py::_build_runtime() | 按 flag 组装 battle stream、LiveBattleIngestor 和可选的 BattleCaptureManager |
| bridge/information/service.py::InformationService.manage_subscription() | 持久化订阅的 desired state；配置提交后调用 _sync_capture() |
| bridge/information/service.py::InformationService._sync_capture() | 从 active 订阅计算消费者集合，调用 source 的同步钩子，并写入 capture-source 与每个订阅的 runtime |
| bridge/information/battles.py::BattleInformationSource.sync_subscriptions() | 只收集需要 battle event 的订阅 ID，检查 battle binding 后调用 manager |
| bridge/information/battles.py::BattleInformationSource.capture_status() | 返回只读 capture snapshot；有 manager 时 mode 为 subscription_managed_live |
| bridge/information/battles.py::BattleInformationSource.close_capture() | 关闭 manager；InformationService.close() 只调用一次且可重复调用 |
| bridge/information/battle_ingest.py::LiveBattleIngestor.refresh() | 增量读取已安装 raw log 并写入本地数据库，不控制 native source |
| bridge/information/battle_capture.py::BattleCaptureManager | 检查安装身份、维护 lease、控制已绑定 producer 的 enable/disable，并持久化恢复 journal |
| tools/control_information_battle_observer.py::run_control() | 执行单次 status、enable 或 disable；native 响应超时返回 unknown_no_retry，不重发 |

manager 的构造函数和公开方法是：

    BattleCaptureManager(installation_path, expected_binding, *, controller=None, journal_path=None)
    reconcile(consumers: set[str]) -> dict
    snapshot() -> dict
    close() -> dict

构造函数本身不访问游戏，也不调用 controller。默认 controller 只有在第一次需要 reconcile 时才延迟导入 run_control。controller 注入值的调用形式是 controller(command, player_ref=None)，实现仍只允许上述三个 command。

snapshot() 不做文件 I/O，也不读取 native status。它返回这些字段：

| 字段 | 含义 |
| --- | --- |
| status | manager 本地状态：idle、active、unavailable 或 closed |
| producer_state | 最近一次已核对的 producer 状态；初始可能为 unknown，发生 latch 后强制为 unavailable |
| managed | 表示服务已显式配置 manager；当前实现恒为 true，不表示 manager 拥有来源或来源当前已启用 |
| owned | 本 manager 是否有已完成且可核验的 enable ownership；外部借用时为 false |
| consumer_count、consumers | 当前需要 battle capture 的订阅数和排序后的订阅 ID |
| reason | 当前状态原因，例如 owned_source、external_source、capture_disabled 或具体 unavailable reason |
| complete | capture/report 完整性字段；manager snapshot 当前为 false，不能用它判断是否已 ready |

对于已配置 manager，服务的 readiness 判断实际看 producer_state == "enabled"。因此要区分“已经配置了管理器”（managed）、“本管理器拥有来源”（owned）和“未来采集可用”（producer state 为 enabled）。

## desired active 与 capture runtime

manage_subscription() 先在 SQLite 中保存订阅配置。创建时，enabled=true 产生 state="active"，否则产生 state="paused"；pause、resume、cancel 只改变订阅的持久化状态和版本。cancelled 订阅不能恢复。

只有同时满足以下条件的订阅才会进入 capture consumer 集合：

1. 订阅的 kind 是 event；
2. event.types 包含当前 EVENT_TYPE，即 battle_observation；
3. 订阅为 active，并且没有 needs_rebind；
4. service context ready 且订阅 binding 与当前 context 相符。

这里的 active 是 LLM 想要的 desired state。capture-source runtime 和订阅 runtime 中的 capture 副本记录的是 manager 观察到的 producer state。它们可能报告 source_unavailable、scope_mismatch 或 world_revalidation_required，所以 active 配置不等于 native 已启用。BattleInformationSource.sync_subscriptions() 在 context ready 但 battle binding 不满足 _bound() 时清空消费者集合；context 暂时不可读时只保留此前已经存在的消费者，不借故授权新的消费者。

配置事务提交后，_sync_capture() 在事务外调用 source hook；这样 SQLite 回滚不会假装撤回已经发布的 native request。tick() 在处理事件前运行同步逻辑。discover、subscription get/list 以及相关状态响应在 source 暴露 managed snapshot 时会带上 capture。

## 首订阅、共享订阅和所有权

下面的流程只针对需要 battle capture 的消费者集合，不针对普通 history query 或其他类型订阅。

1. 首个非空消费者集合到来时，manager 取得 installation 目录旁的 information-battle-capture.lock。Windows 使用 msvcrt，其他平台使用 fcntl；同一进程另有本地 guard。拿不到锁时返回 unavailable，且不发送 native command。
2. manager 读取 installation 文件和一次 status，核对 installation、generation、进程 PID/creation、game SHA、DLL SHA 以及 status binding。对于 enable/disable，使用的 player_ref 必须来自当前 status["binding"]["player_ref"]。
3. status 为 enabled 且没有本 manager 已完成的 ownership journal 时，来源被标记为 external_source 并借用。owned=false，但 producer 已 enabled，订阅仍可 ready；最后一个消费者释放时不会 disable。
4. status 为 disabled，且已有 bootstrap binding、没有旧消费者占用时，manager 先写 pending-enable，再发送一次 enable。只有收到 accepted、正确 state、正确身份和 nonce 的响应后，才写 completed-enabled 并置 owned=true。
5. 多个订阅只共享这一份 producer lease。重复 reconcile 不会再次 enable；取消或暂停其中一个订阅，只从消费者集合移除它，剩余消费者仍会保持 producer enabled。
6. 最后一个消费者释放时，只有 owned=true 且当前身份仍然正确的来源才会执行一次 pending-disable、一次 disable，并写 completed-disabled。外部来源不执行 disable。

ready 或 cold 但没有满足绑定条件的 native 来源不会被盲目 enable。消费者存在期间，如果 status 变成 disabled、source_changed、fault 或身份校验失败，manager 会 latch 为 unavailable，不在后台反复 enable。close() 清空消费者、在安全且有 ownership 时执行最后释放，然后释放 lock；调用是幂等的。

控制响应可能先于下一次状态文件更新到达。控制器用读取前的文件时间返回 `observed_at_ns`；完成一次启停后，manager 只接受晚于 journal 中完成时间的新状态。等待最多3秒，只重复读取状态，不重发控制。这样，立即恢复订阅时，关闭前的旧 `enabled` 状态不会被误判为外部来源。

## journal 和中断恢复

默认 journal 是 installation 文件同目录下的 information-battle-capture-journal.json，也可通过 journal_path 指定。manager 使用临时文件、os.replace 和 fsync 原子更新 journal。journal identity 绑定 installation 路径、installation/generation、当前进程 PID/creation、game SHA 和 DLL SHA；旧进程或旧代际的 journal 不能控制新进程。

关键状态如下：

| journal state | 恢复规则 |
| --- | --- |
| pending-enable、unknown-enable、unknown-status | 状态或 ownership 不确定，返回 unavailable；不重发 enable |
| completed-enabled 且 owned=true | 只有 identity 完全相同且当前 status 仍为 enabled 时，才恢复本 manager 的 ownership；不发新的 enable |
| pending-disable、unknown-disable | disable 结果不确定，返回 unavailable；不重发 disable，也不猜测已关闭 |
| completed-disabled | 没有旧 ownership；下一轮新的消费者可以在重新核对绑定后走一次 enable |

写入 pending 发生在单次 native command 之前。native bridge 超时会留下 unknown_no_retry 语义；manager 将它记录为 unknown journal 并 latch。close() 遇到 unknown 不会再 dispatch。这样可以避免进程重启后把一次已经可能生效的 request 当作从未发送，再次改变来源状态。

## native 身份与 observer 身份

物理 POR 是 native binding 中标识真实已安装 producer 的 full reference，当前代码从 status["binding"]["player_ref"] 取得它。这个值还必须与 installation、generation、PID/creation 及哈希身份一致。

--observer FRA 是服务的 observer country tag，用于 context、查询 scope 和战报参与者筛选。它不是 native player_ref。expected_binding 中可能保留历史 observer_ref，但 BattleCaptureManager 绝不把它发送给 run_control。因此，不能把 FRA 或 observer ref 填入 --player-ref；控制桥要求的是绑定返回的 16 位十六进制 physical-player fullref。

## 数据库读取、自然战斗和暂停游标

LiveBattleIngestor.refresh() 只负责把安装来源已经产生的 raw log 追加到 battle SQLite。BattleInformationSource._refresh() 在 battle binding 通过时调用它，已有提交记录在 ingest 暂时失败时仍可读取，但会带 acquisition gap。manager 不负责刷新数据库；service/source 的 poll 路径负责把采集到的记录投影成 B01/B04 事件。

因此，当前 v30 交接记录所示 producer 为 disabled 时：

- 配置 --battle-stream（可选再配置 --battle-ingest-installation）后，新订阅仍可读取已保留的 SQLite 记录；
- 只有 ingest flag 并不会开启 producer，所以没有新的 native 战斗记录可写入数据库；
- 加 --battle-manage-capture 后，只有在安装身份、绑定和 native status 都通过，且首个 event consumer 的一次 enable 被 accepted 并记录为 owned，未来自然战斗才具备采集条件；
- 如果实际来源是外部已启用的 producer，manager 可以借用它并报告 owned=false；这不等于服务拥有关闭它的权利。

事件消费使用共享的 event-source cursor 和 pending 队列。暂停某个 subscription 会使它不再匹配新的 event，但不会为它建立独立的历史 cursor。如果另一个 active event consumer 继续消费，shared cursor 可能已经前进；恢复暂停订阅时，系统不保证把暂停期间的全部战斗 backfill。paused 表示 desired subscription state；若它是最后一个 capture consumer，manager 可能按 ownership 规则释放来源，若仍有其他 consumer 或来源是外部借用，则 producer 可以继续 enabled。paused 本身也不保证恢复时能重放所有遗漏事件。
