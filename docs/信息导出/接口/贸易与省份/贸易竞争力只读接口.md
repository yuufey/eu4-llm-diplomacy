# 贸易竞争力只读接口

通过 `T04`，AI 可以按贸易节点查询 FRA 的竞争力、节点总竞争力、原生份额和来源明细，
对应字段为 `country_power`、`total_power`、`shares` 和 `sources`。当前香槟节点的主贸易
城市加成为5点，转入明细为来自ORL的51.131点；来源条目保留数量、单位和国家引用。
接口固定于 EU4 `1.37.4`，读取原生缓存，不调用游戏函数或写入游戏状态。

当前覆盖是 `partial`，四个字段的 `complete` 都是 `false`。缓存的刷新时机尚未证明，
静态 UI selector 与观察方国家 fullref 的实时相等关系也尚未证明，因此不能把本接口
标记为完整 GUI 复现。`shares`、`sources` 也保持 `partial` 且 `complete=false`；
竞争国选择和其他国家范围仍未实现。

本批的 `sources` 公开值包含 `rows`、`capital_status`、`dynamic_sources` 和按容器
方向拆分的 `transfer_sources.to`/`from`。外层 `unit` 是 `mixed`：已闭合的来源行、
Main Trade City 和转移链使用 `trade_power`，动态项的单位仍是 `unknown`。当前独立
原始参考中 80 个节点的动态链表头都为空；这只说明本次观察到空链，不把动态数量的
单位或非空路径标记为已闭合。动态名称在满足严格 key 条件且中性本地化读取成功时
可以返回 literal；当前样本没有非空动态名称可作为实机正例。`multiplier` 仍显式返回
`unknown`。

## 查询范围与对象

请求的主题为 `T04`，对象必须是带稳定 ASCII `node_id` 的贸易节点。参数对象必须是
空对象；例如：

```json
{
  "request_id": "trade-power-query-001",
  "queries": [
    {
      "topic": "T04",
      "object": {"type": "trade_node", "node_id": "champagne"},
      "fields": ["country_power", "total_power", "shares", "sources"],
      "parameters": {}
    }
  ]
}
```

这是 `information_query` 的完整参数 JSON。`node_id` 不存在时返回字段级
`{"status":"unknown","reason":"NODE_NOT_FOUND"}`，不会用零代替缺失节点。观察方
必须是 `FRA`；当前适配器不接受国家对象来代替贸易节点对象。

## 字段和数值

两个竞争力标量、份额条目和各来源行都保留有符号 32 位原始整数。`raw_hex` 是该整数的四字节小端编码，负数使用
二进制补码；可读数值为 `raw / scale`。`shares` 和 `sources` 在国家集合内保存这些值。
`sources` 的字段级 `unit` 为 `mixed`；`rows`、`capital_status` 和转移项的可读数值使用
`unit="trade_power"`、`scale=1000`，动态项使用 `unit="unknown"`、`scale=1000`。

| 字段 | 含义 | `value_origin` |
| --- | --- | --- |
| `country_power` | 指定节点中 FRA 条目的当前竞争力派生值 | `derived_from_copied_native_caches` |
| `total_power` | 指定节点的当前总贸易力缓存原值 | `copied_native_cache` |

两字段共同返回以下语义键：

```json
{
  "status": "known",
  "value": 174898,
  "raw": 174898,
  "raw_hex": "32ab0200",
  "unit": "trade_power",
  "scale": 1000,
  "period": "current",
  "basis": "native_trade_node_power_caches",
  "value_origin": "derived_from_copied_native_caches",
  "complete": false
}
```

上例是 `country_power` 的形状；`total_power` 使用相同的键，但其来源为
`copied_native_cache`。当前 `champagne` 的独立原始参考值为：

```json
{
  "country_power": {"raw": 174898, "raw_hex": "32ab0200"},
  "total_power": {"raw": 746110, "raw_hex": "7e620b00"}
}
```

这些数值来自独立两遍原始采样和有界静态公式；公开接口的历史实机对照结果见文末。
这不构成实时 GUI 等价证明。不要用
`country_power / total_power` 代替原生份额缓存；两种缓存之间的口径和刷新关系尚未证明。

## `shares` 与 `sources`

这两个字段读取同一贸易节点的 FRA 条目缓存。`shares` 保留条目 `+0x2c` 的 signed32
原值，把它按 `scale=1000` 解释为 `ratio`；原值为零时仍返回 `known` 和零，不能用
`country_power / total_power` 重新计算它。`sources` 的外层 `unit` 为 `mixed`，其
`FRA` 值由四个公开容器和一个未闭合的 `multiplier` 组成：

```json
{
  "shares": {
    "status": "known",
    "value": {
      "FRA": {"raw": 348, "raw_hex": "5c010000", "unit": "ratio", "scale": 1000}
    },
    "unit": "ratio",
    "scale": 1000,
    "period": "current",
    "basis": "native_trade_node_share_and_source_caches",
    "value_origin": "copied_native_cache",
    "complete": false
  },
  "sources": {
    "status": "known",
    "value": {
      "FRA": {
        "rows": [
          {"native_key": "TP_PROVINCE_POWER", "raw": 60538, "raw_hex": "7aec0000", "unit": "trade_power", "scale": 1000},
          {"native_key": "TRADE_POWER_CAPITAL", "raw": 5000, "raw_hex": "88130000", "unit": "trade_power", "scale": 1000}
        ],
        "capital_status": {
          "status": "known", "included": true, "raw": 5000,
          "raw_hex": "88130000", "unit": "trade_power", "scale": 1000
        },
        "dynamic_sources": {"status": "known", "items": []},
        "transfer_sources": {
          "to": {"status": "known", "items": []},
          "from": {
            "status": "known",
            "items": [
              {
                "country": "ORL", "fullref_raw_hex": "4f524c007e000001", "slot": 126,
                "raw": 51131, "raw_hex": "bbc70000", "unit": "trade_power",
                "scale": 1000, "native_key": "TRANSFER_TRADE_POWER_FROM", "direction": "from"
              }
            ]
          }
        },
        "multiplier": {"status": "unknown", "reason": "TRADE_MULTIPLIER_NOT_CLOSED"}
      }
    },
    "unit": "mixed",
    "scale": 1000,
    "period": "current",
    "basis": "native_trade_node_share_and_source_caches",
    "value_origin": "copied_native_cache",
    "complete": false
  }
}
```

上例使用独立 v3 raw reference 中 `champagne` 的真实缓存形状，并按公开适配器的字段
投影展示。`TP_PROVINCE_POWER` 和 `TP_SHIP_POWER` 只有在对应 signed32 缓存不为零时
写入 `rows`；`MERCHANT_DOWNSTREAM_BONUS` 只有在缓存大于零时写入。未写入的行不等于
把原值改成了零。四种来源行的静态键为 `TP_PROVINCE_POWER`、`TP_SHIP_POWER`、
`TRADE_POWER_CAPITAL` 和 `MERCHANT_DOWNSTREAM_BONUS`，行值均为复制的
`trade_power` 缓存；它们不是完整来源清单，也不能相加后冒充节点总竞争力。

`TRADE_POWER_CAPITAL` 对应英文原生标签 `Main Trade City in area`。全局 signed32
原值 `5000` 按 `scale=1000` 是 5 点，只在 FRA 的 country anchor 与选定节点 runtime
pointer 相等时作为 `capital_status.included=true` 并进入 `rows`。节点不匹配时，
`capital_status` 仍可为 `known`，但 `included=false` 且不公开该行的原值；这不是
通用“首都”字段。

`dynamic_sources` 的每个项目公开 `raw`、`raw_hex`、`unit="unknown"`、`scale=1000`
及一个名称对象。数量仍是独立缓存值，不能从名称或名称解析结果推断单位。当前 80
节点观察到的 entry `+0x90` 链表头均为空，因此公开结果为 `status="known"`、
`items=[]`；这不闭合动态来源的数量单位或非空路径。

### 动态来源名称读取

名称读取使用项目保存的 `name_raw_hex`，与动态数量读取属于两次有界 capture，结果不
宣称原子一致。适配器先要求恰好一个终止 NUL 且无嵌入 NUL，去除终止符后剩余长度为
1至160字节，且每个字节是可打印 ASCII；相同 key 在批量请求中去重。通过筛选的 key 交给中性
[`NativeLocalizationReader`](../../../../bridge/information/native_localization.py)，不调用
mission 分支或 custom resolver。

本地化读取成功且条目是 literal 时，名称对象保留 key、原始 key 字节、语言、codec、
解码前模板字节和 reader 审计信息，并增加 decoded literal `value`。下面是结果形状
示例，不是当前实机条目；审计信息仅列部分键，`codec`、语言和审计内容以该次已验证 session 返回为准：

```json
{
  "status": "known",
  "key": "TRADE_SOURCE_EXAMPLE",
  "raw_hex": "54524144455f534f555243455f4558414d504c4500",
  "language": "l_english",
  "codec": "utf8",
  "raw_template_hex": "547261646520736f75726365",
  "reader_provenance": {
    "reader": "bounded_ReadProcessMemory",
    "codec": "utf8",
    "atomic_with_task_slots": false,
    "atomic_across_batches": false,
    "world_generation_verified": false
  },
  "value": "Trade source"
}
```

缺失 key、非法字节、模板/动态 token 或 reader/guard 失败时，名称保持
`status="unknown"`，并尽可能保留 `key`、`raw_hex`、`language`、`codec`、
`raw_template_hex`、`reader_provenance` 和具体 `reason`；数量的 `raw`/`raw_hex` 仍
按原生记录保留。任一名称读取或数量读取后的 context 发生变化，适配器会撤回该次
查询请求的所有字段。当前归档的 80 节点 raw 参考没有非空动态项目，所以不在文档中
伪造非空实机示例。

`transfer_sources` 的 `to` 和 `from` 是两个独立容器，方向由容器确定，原始 signed32
值和正负号原样保留，不能按方向再次取反。转移项目只有在其 fullref 与 country table
对应槽位对象的 fullref 精确相等后才公开 `country` 标签；独立 v3 参考中的 `ORL`、
`AUV` 均满足这一 guard。`to`/`from` 项仍只表示已读取的原生转移缓存，不能推导
完整贸易力或份额。

`shares` 的静态来源是 entry `+0x2c` 的百分比/detail 路径；`B58D00` 的返回值会把
`+0x2c` 与另一个对象标量及可选 factor 组合，并沿 `income` 选择器使用，因此文档不
把它命名为 share。三个固定来源行分别来自 entry `+0x28`、`+0x1c` 和 `+0x40`，单位
均为 `trade_power`、scale 为 `1000`。这些值是当前 native cache 的复制结果；刷新时机、
UI selector 与观察方 fullref 的实时对应关系尚未证明，所以四个字段都保持
`partial`/`complete=false`。

## `country_power` 的原生运算顺序

每个节点条目的 `+0x44`、`+0x48`、`+0x4c`、`+0x50`、`+0x54` 都按 signed32 读取。
固定 PE 的两个 UI 计算路径在除法后的 `EDX` 上执行 `TEST EDX,EDX` 和
`CMOVG R8D,EDX`，所以必须先把 signed64 商窄化为 signed32，再按窄化结果判断正数：

```text
a       = i32(entry + 0x44)
c       = i32(entry + 0x4c)
q64     = trunc0(i64(a) * i64(c) / 1000)
q32     = i32(q64)
positive32 = q32 if q32 > 0 else 0
cap     = signed_min(i32(entry + 0x48), positive32)
delta   = i32(entry + 0x54 - entry + 0x50)
result  = i32(cap + delta)
```

`+0x50` 到 `+0x54` 的差值以及最后加法都在 32 位有符号回绕语义下处理。不能把
测试写成“先判断 `q64 > 0` 再窄化”，也不能把 cap 放到 delta 之后或把总节点值当作
份额分母。`total_power` 则直接复制 runtime node `+0xc8` 的 signed32 值，再由
`scale=1000` 表示可读数。

一个能区分窄化顺序的纯计算反例是：`0x44=2000000000`、`0x4c=2000000000`，此时
`q64=4000000000000000`，但 `q32=-1827012608`，因此原生 `TEST/CMOVG` 走零分支，
`positive32=0`；不能按未窄化的正 `q64` 取值。

## 报告配置

报告创建也必须提交完整的 `name`、`queries` 和 `detail`。`detail` 可用 `raw`、
`brief` 或 `full`；下面保存四个字段的原始结果：

```json
{
  "request_id": "trade-power-report-create-001",
  "operation": "create",
  "config": {
    "name": "FRA champagne trade power",
    "queries": [
      {
        "topic": "T04",
        "object": {"type": "trade_node", "node_id": "champagne"},
      "fields": ["country_power", "total_power", "shares", "sources"],
        "parameters": {}
      }
    ],
    "detail": "raw"
  }
}
```

服务返回报告对象的 `id` 后，可以用它复用同一份配置。下例 ID 来自本次验收，调用时应替换为实际返回的 ID：

```json
{
  "request_id": "trade-power-query-report-001",
  "report_id": "report-40a0d89b1fee4e07aaec54ba3d7c9d09"
}
```

报告中的来源上下文仍会重新校验会话、观察方、版本、profile guard、缓存记录和读取
前后的 context；失败时字段保留 `unknown` 或 `unavailable` 原因，不沿用旧值。

## 周期订阅

T04 当前声明 `query` 和 `periodic`，不声明 `event` 或 `change`。创建周期订阅时，
`name`、`kind`、`report_id`、`enabled` 和完整的 `schedule` 都必须提供；实时会话的
绑定值应以 `information_discover` 返回的当前上下文替换示例值：

```json
{
  "request_id": "trade-power-subscription-create-001",
  "operation": "create",
  "config": {
    "name": "FRA champagne trade power every 2 seconds",
    "kind": "periodic",
    "report_id": "report-40a0d89b1fee4e07aaec54ba3d7c9d09",
    "enabled": true,
    "binding": {
      "session_id": "31460-1dd653f69242d7b",
      "observer": "FRA",
      "game_version": "1.37.4"
    },
    "schedule": {
      "basis": "real",
      "every": 2,
      "unit": "seconds",
      "missed": "coalesce"
    }
  }
}
```

这里的 `session_id` 仅是当前独立 raw reference 的身份示例，不能替代实时发现结果。
`missed="coalesce"` 表示错过的到期读取合并处理；周期读取不会推进游戏日期，也不会
执行外交或其他业务动作。订阅结果仍保持 `partial` 和 `complete=false`，直到缓存新鲜
度与 UI selector 对齐得到独立证据。
