# 原始功能与验收要求

整理日期为2026-11-07。本页从整理前计划提取功能范围、阶段和验收正文，保留需求措辞，并调整迁移后的相对链接。完整整理前版本见[原文封存](../../历史归档/2026-11-07整理前/信息导出与订阅开发计划.md)。

本页正文用于历史追溯，当前交付范围与验证节奏按用户最新的宏观战略原则调整，见[当前计划](信息导出与订阅开发计划.md)及[范围审查](宏观战略信息范围审查.md)。

## 本轮确定的范围

| 本轮确定 | 后续再选择的策略 |
| --- | --- |
| 统一的信息目录、查询参数和结果格式 | 向 LLM 发送完整状态、增量、摘要或其组合 |
| 定期、即时和主动查询三种入口可以并存 | 维护一份文件、生成多份文件、使用其他存储或交付方式 |
| 多个周期任务可以并行配置，简报与报告共用信息来源 | 每次结果产生是否唤起 LLM，以及具体唤起与对话组织方式 |
| LLM 能发现信息能力并自行管理订阅和配置 | 小变化合并、重要性阈值、报告正文组织和历史保留期限 |
| 状态信息与事件信息有明确身份、时间和完整性 | 默认向 LLM 提供多大范围的世界状态、怎样形成长期记忆 |
| 同一信息来源能够被多个查询和订阅复用 | 特定国家的战略偏好、任务优先级和贸易目标排序 |

框架可以有运行所需的最小输出适配器和配置保存方式，但这些属于可替换实现。首批验收不要求决定长期文件布局、自动唤起 LLM 或采用增量协议；输出适配器接收结果，也不等于 LLM 已经阅读或作出决定。

## 总体结构与职责

```text
Mod 脚本、原生只读查询、静态规则、现有桥接状态
                       ↓
                信息采集适配器
                       ↓
          统一信息目录、查询与事件处理
                       ↑
       定期调度 / 事件触发 / LLM 主动查询
                       ↑
            配置管理与 LLM 订阅管理
                       ↓
              统一结果 → 输出适配器
```

| 组件 | 责任 | 与其他组件的关系 |
| --- | --- | --- |
| 信息能力目录 | 登记主题、字段、对象、参数、支持版本、来源、可知范围及可用触发方式 | 查询与订阅都先通过目录校验；不能把计划字段当作可用字段 |
| 采集适配器 | 从既有 Mod、原生查询、静态配置或历史记录取得信息 | 负责具体来源、单位与语义，不自行决定何时唤起 LLM |
| 查询服务 | 解析对象和字段，组织读取并返回统一结果 | 主动查询和定期任务共用；既有外交预览可由适配器接入 |
| 事件处理 | 接收并识别已采集的事件，保留身份、顺序和完整性，匹配订阅 | 区分事件产生、采集和交付；不能用低频状态轮询冒充完整事件捕获 |
| 调度服务 | 按配置生成到期的导出任务，支持多个不同周期 | 不把简报和长报告实现成两套采集系统 |
| 订阅与配置管理 | 接受用户及 LLM 的查询、修改、启停和取消操作，返回有效配置 | 正常配置变更可在运行中生效，不要求每次重启或人工改文件 |
| 输出适配器 | 将统一结果交给外层消费端，并报告交付状态 | 为以后选择文件维护、工具返回或其他交付方式保留边界 |

复用现有 [bridge/diplomacy_api.py](../../../bridge/diplomacy_api.py) 等入口中已经验证的查询能力；这些入口继续保留其原有业务语义。新信息服务组织读取，不通过执行外交动作来获取信息，也不将原生执行效果当作状态查询。

## 首批必须交付的功能

### 信息发现与主动查询

LLM 必须能查看当前实际可用的信息主题、字段、参数、对象范围和能力状态，再发起一次性查询。能力目录可以展示待开发条目，但要与可调用部分明确区分。

查询结果至少说明本次请求、游戏会话和版本、观察方、涉及对象、游戏日期、采集时间、来源及完整性。未知、不可见、不适用、暂时不可用、过期和真实的零值或空集合分别表达；部分成功保留已取得内容及缺项，不能伪造完整结果。

允许查询指定国家、国家对、省份、战争、贸易节点等有明确语义的对象。具体支持哪些对象与筛选器由能力目录声明。查询不会推进游戏日期或自动回应外交请求。

### 多频率定期导出

首批支持创建多个独立周期任务。每个任务可选择信息范围、报告配置、时间基准、周期和启停状态；短周期简报与长周期报告可以同时存在。

时间基准需要明确区分游戏时间和现实时间。游戏暂停、加速、跨过多个到期点、读档或切换会话时，调度状态与本次处理方式应可查询；实际支持的单位和漏期处理选项由配置能力声明。不得为了满足周期而自行推进游戏。

“简报”和“报告”首先是可配置的信息集合与详细程度，不预设必须使用另一个 LLM 来撰写正文。示例中的每周简报、每季报告仅用于验收多频率能力，不是最终默认策略。

### 即时导出

即时导出由信息变化或事件采集触发，与定期任务独立配置。首批建立事件接入、类型过滤、订阅匹配、结果生成和状态查询的公共路径，用已有可核对来源贯通。

能力目录应分别说明原生事件通知、变化检测和周期轮询的性质。不能把一个依赖定期轮询的来源无条件标为逐场即时捕获。逐场战报等事件在启用采集时，需要在原始内容消失前取得必要信息；何时向 LLM 汇总发送不改变这一采集要求。

### LLM 自主订阅与配置管理

LLM 可以直接通过工具或接口进行以下操作，正常有效的配置变更不再要求用户手工修改文件或逐次批准：

- 发现支持的主题、对象、字段、事件类型、周期和配置参数。
- 创建订阅，读取、列出和修改自己的订阅，暂停、恢复或取消订阅。
- 配置所关心的国家、关系、战争、节点、事件类型或字段集合，以及支持的筛选条件。
- 同时维护多个不同频率的定期任务和即时事件订阅。
- 查看当前有效配置、配置版本、变更结果及适用范围。
- 查看订阅最近一次尝试、生成结果、失败原因和交付状态。

每个订阅有稳定编号，重复请求和修改应有明确结果。配置更新先校验完整性、来源能力和参数，再整体生效；失败时保留原配置并返回原因。原子性与可查询的配置版本用于避免一半字段生效、一半未生效。

配置应能在服务正常重启后恢复；具体保存介质可以后换。恢复配置后，必须重新核对当前游戏版本、观察方和会话适用性，不能把旧游戏的事件游标、对象地址或待回应请求直接带入新会话。

订阅控制信息获取与导出，不授予额外的外交执行权限，也不能扩大本国在游戏中的可知范围。取消一个订阅不应误停其他订阅共用的来源；启停采集、保存和交付各自的语义应明确。

### 首批拟提供的接口组

以下为职责级接口清单，最终工具名称和请求 schema 在开发第零阶段确定。

| 接口组 | 首批操作 |
| --- | --- |
| 能力目录 | 列出主题和字段，读取参数、对象、版本、来源及触发能力 |
| 主动查询 | 一次性读取指定信息，查询请求结果与完整性 |
| 报告配置 | 创建、读取、修改和删除信息集合及详细程度配置；处理被任务引用时的变更 |
| 订阅管理 | 创建、读取、列出、修改、暂停、恢复和取消订阅 |
| 调度与导出配置 | 创建、读取、修改和删除独立任务或配置组，配置频率、时间基准、范围、启停及支持的输出参数；全局项支持读取、修改和清除覆盖值 |
| 运行状态 | 查看实际有效配置、下次到期、最近尝试、结果和失败原因 |

订阅、报告配置和一次性查询使用同一信息模型。创建订阅成功、调度到期、采集完成、生成结果和交付给输出端必须分别报告，不能用“已创建”代替“已经取得并交付信息”。

## 开发阶段与完成标准

### 阶段零 核对来源并确定公共合同

1. 以信息目录编号为索引，登记所需字段、来源、支持状态和版本约束。
2. 核对现有 Mod 快照、原生查询和事件记录可复用的部分，区分静态定义、实时状态、条件判断和推算结果。
3. 确定主题标识、对象身份、查询结果、配置、订阅及运行状态的最小 schema。
4. 确定采集适配器与输出适配器的接入合同，列出首批用于贯通的真实来源。

完成标准：开发者能据此独立实现适配器与调度，不需要先决定增量、文件布局或 LLM 唤起方式；现有实现与待开发内容可逐项查询。

### 阶段一 交付通用框架与自主订阅

1. 实现信息能力目录、一次性查询和统一结果。
2. 实现多周期调度、报告配置和即时事件处理路径。
3. 实现订阅与配置的完整管理操作、运行中变更、保存及恢复。
4. 接入至少一种已有真实状态来源，以及一种已有可核对的真实事件或请求来源，贯通输出适配器。
5. 向 LLM 暴露能力发现、查询、订阅和配置工具，而不只提供命令行或内部函数。

首批完成标准如下；未接入的后续字段必须如实返回状态，不允许用样例数据冒充真实采集。

| 场景 | 必须可观察到的结果 |
| --- | --- |
| LLM 发现信息能力并主动查询 | 返回对应真实来源结果，包含对象、时间和完整性 |
| LLM 创建短周期简报与长周期报告 | 两个周期独立生效，均通过同一查询与结果路径生成内容 |
| LLM 修改其中一个周期或字段范围 | 返回生效配置与版本；另一个任务不被误改 |
| LLM 订阅某个已支持类型的事件 | 已捕获的匹配事件触发对应结果，其他订阅继续正常运行 |
| 同一真实状态来源启用变化检测 | 变化能够触发配置的导出，并明确检测方式、采样间隔或原生触发时点，不冒称轮询期间的每次变化都已捕获 |
| LLM 暂停、恢复或取消订阅 | 运行行为与可查询状态一致，不继续生成已取消订阅的新任务 |
| 配置请求重复、参数无效或能力不支持 | 返回明确结果，不产生重复任务或半生效配置 |
| 服务重启、游戏暂停或会话变化 | 恢复和调度行为可解释，过期对象或旧会话数据不冒充当前数据 |
| 读取失败、部分结果或输出失败 | 缺项与失败可查询，不标为成功交付 |

### 阶段二 扩展状态与规则信息接口

在公共合同稳定后，按信息目录接入基础状态、关系、任务、修正、贸易和行动预览。下面给出覆盖分组，实施时在对应编号下继续拆分字段与适配器任务。

| 目录范围 | 主要工作 | 完成依据 |
| --- | --- | --- |
| C01–C04 | 决策背景、观察方、会话、有关对象和局势变化 | 身份与时间范围正确，目标输入与游戏事实分开 |
| N01–N09、F01–F04 | 本外国力、资源、国内约束、当前修正及期限 | 单位、方向、可见性和修正来源明确，数值与界面或独立来源核对 |
| R01–R07 | 关系网、好感、信任、人情和承诺 | 双边方向与集合完整性明确，期限及缺项可辨 |
| M01–M05 | 扮演国实际任务树、前置、条件、状态、目标和奖励 | 区分静态定义与当前生效分支，能对应实际任务界面 |
| G01–G05、T01–T06 | 领土利益、贸易线路与相邻节点、节点价值及竞争力 | 静态线路与实时数值分开，竞争力、价值与本国收入不混用 |
| D01–D06 | 宣战理由、规则、参战方案、意愿及代价 | 针对完整具体方案查询，不发起宣战 |
| W01–W04、P01–P06 | 战争状态、分数、承受能力、议和候选及后果 | 绑定战争和视角，参数变化后正确重算，预览与实际效果分开 |
| A01–A05 | 日常外交选项、费用、提议、回应和结果 | 复用已有查询与记录，不因查询或订阅而执行动作 |
| S01–S05 | 相关制度、宗教、属国、继承及特殊外交条件 | 不适用条件可表达，相关国家能取得必要字段 |
| H01–H04 | 变化历史、到期事件、趋势及既有决策记录 | 说明历史来源与时间跨度，推算保留输入和缺项 |

完成标准：接入的主题不为定期、即时和主动查询各写一份不同的采集实现；具体支持哪些触发方式由来源能力决定，LLM 可通过首批接口发现和使用。

### 阶段三 补齐逐场事件与即时通知来源

1. 为 B01–B04 补齐每场陆海战结束时的完整结果采集，覆盖双方、胜负、数量、损失和实际展示的其他结果。
2. 补齐外交请求、参战召唤、撤回、过期和实际回应等生命周期通知；同时明确是否已有受控国回应挂起机制。
3. 补齐宿敌变化、宣战、关系变化、本国修正新增或失效、任务进展等所需即时来源。
4. 为每种来源核对事件身份、相关战争和国家、可见范围、顺序、重复及断档。

依赖研究见[弹窗分类与外部决策研究](../实现研究/国家与国内/弹窗分类与外部决策研究.md)。其中原生路径属于指定版本的静态证据；不把消息 key、通知钩子或已定位函数直接登记为完整内容导出能力。

完成标准：每类事件至少有对应的原始内容与导出结果核对。逐场战报不能只提供累计战争分或最终兵力，参战召唤入站不能用出站召集盟友替代，配置为低频报告时也不能漏掉采集期间发生的必需事件。这里完成信息与待处理状态导出；新增选项执行或回应权限本身另按原有外交权限合同实现和验收，不作为信息查询的副作用。

### 阶段四 整体验收并形成可使用接口

1. 按目录逐项核对字段覆盖、接口调用、可知范围、支持版本和实际证据。
2. 用同一来源交叉检查主动查询、不同周期报告和即时订阅的对象与数值语义。
3. 覆盖多订阅、重叠范围、并发查询、配置热更新、重启、读档及失败恢复。
4. 完成工具说明与实例，让 LLM 能自行发现、配置和使用实际支持的信息。

“框架完成”和“全部目标信息可导出”是两个里程碑。最终需要对目录中全部 74 项建立可调用入口及字段级覆盖记录；确属不可见或不适用的信息说明条件。对属于目标范围、应可知但尚未实现的内容，保留未完成状态，不能只注册名称或返回 `unsupported` 就算完成。

### 后续阶段 聚合查询

在原子信息接口具备后，实现可组合的一次查询多类信息：

- **英格兰概况**：一次返回其相关身份、国力、战争、依附关系、与本国关系及其他已支持信息。
- **周边强国对本国的好感一览**：先按明确的周边范围和强国标准选出对象，再返回这些国家对本国的好感及所需明细。
- **战争或贸易区域概况**：复用已支持主题，按同一上下文返回多项结果。

聚合层组织既有原子查询，不另造一套状态读取和权限判断。多来源时间不一致、部分字段缺失或对象选择条件不明确时应如实说明；“周边”和“强国”的定义作为参数或可见配置提供。此阶段不阻塞首批自主订阅交付。

## 验证与版本约束

开发时按改动运行有意义的定向测试，框架重点验证周期、订阅状态、配置生效、能力协商、对象隔离和失败传播。事件匹配与调度可使用记录数据验证，但记录回放或 fixture 通过不能代替游戏实时采集结果。

每批适配器分别核对静态定义、实际读取和业务含义；涉及原生版本时绑定 EXE SHA-256、DLL 与会话身份。1.37.4 和 1.37.5 分别维护支持情况，不把地址或运行证据跨版本继承。正式批次按现有流程运行 `python -m pytest -q bridge/tests`，如实区分新增失败、已有环境或缺失证据导致的问题。

实时验证继续遵守 [HANDOFF](../../../HANDOFF.md)、[原生资源限制](../../../work/AGENTS.md)和既有不重放规则。需要运行环境时优先使用只读采集或合规的新测试场景；不为验证导出而重放历史成功、已派发、未知或所有权未闭合的外交动作。

## 开始实施时的第一组任务

1. 建立信息能力与目录编号的对应表，选定首批真实来源及其适用版本。
2. 确定查询、订阅、配置和结果状态的公共 schema，补齐最小合同测试。
3. 贯通一条真实状态查询及多频率调度，再贯通一条已知事件的订阅输出。
4. 将订阅与配置的完整管理操作暴露给 LLM，完成首批验收表。
5. 按阶段二和阶段三扩展具体信息来源，持续更新字段覆盖记录。

本计划保留采集、调度、订阅和输出之间的明确边界。增量或完整导出、长期文件维护、报告呈现及 LLM 唤起策略，在框架可用后继续讨论和选择。
