# 逐场战报的结果对象与采集路径

2026-10-25 第十六批沿模板、消息移动、提交及窗口构造继续取得七条静态证据，并实现通用记录的JSONL编码和SQLite接收保存，离线组合测试通过。原生日志使用独立的`_LOG`模板，尚不能替代完整结果框内容；真实采集和生产事件源仍未接入。详见[消息与传输说明](逐场战报消息与传输.md)，B01–B04保持planned。

2026-10-25 第十五批继续核对了侧国家选择、指挥官选择、海战舰船转移及条件清理，并新增带下游确认的队列排出组件。结果侧会重排，俘获路径会使用随机数和修改游戏，静态同步调用也不证明回调期间的合法寿命。完整证据与实现边界见[采集与交付说明](逐场战报采集与交付边界.md)。尚未安装战报钩子或接入生产事件源，B01–B04仍为planned。

2026-10-25 第十三批已继续核对结果对象初始化、保存函数和陆战格式器，并实现供未来采集使用的有界复制队列。队列已通过独立编译和双线程测试，尚未连接原生战报钩子。B01–B04 继续为 `planned`；现有外交日志、累计战争分、界面控件或框架中的示例事件都不能替代逐场战报。

本文仅适用于 EU4 1.37.4、EXE SHA-256 `b23fa0e1f698d31b01cdd1c3817a675805d8c6286cb66f9c231e6e2a42544d77`。静态映像基址为 `0x140000000`。正文函数地址均为 RVA，静态 VA 为基址加 RVA；运行地址须重新绑定模块身份。每个函数的完整多段范围、包含端点约定、Evidence ID 和原始文件 SHA 见[研究索引](../../../work/runtime/information-battles-20261025-001/research-index-001.json)。下述结论均为静态观察或明确标注的推断，没有游戏执行证据。

## 已闭合的调用关系

```text
23A020：包含 SetupResults 诊断的路由
  → 237D80：包含 SetupNonSiegeResults 诊断的构造路径
      → 237FC0：分配并填充结果对象、部分栈上汇总值
      → 237950：按双方或战争成员累加辅助值，含单位分支
      → 2367A0 / 236DC0：尚未逐函数分析的汇总路径
  → 238620：按参与方处理临时变量及后续回调
  → kind=2：22E6B0，含 NAVALBATTLEOVER 的海战消息格式器
  → kind=1：232A80，含 LANDBATTLEOVER 的陆战消息格式器
  → 在特定保留条件不成立时，调用结果对象的虚析构入口
```

路由 `23A020` 检查战斗对象 `+0x44`；若已置位则返回，否则先写1再继续。它通过虚表 `+0x60` 的返回值选择类型，观察到1进入陆战格式器、2进入海战格式器；不能把未展开的其他类型自行命名。`237D80` 在任一侧参与者容器为空时返回0。路由只在构造成功时继续处理结果。

路由中的栈上汇总值、`237FC0` 返回的结果对象和战斗对象是三个不同对象。海战格式器的第二参数对应栈上汇总值，第三参数对应结果对象，不能混用同一偏移的含义。`237950` 的原始研究目录暂名为 `rea-battle-loss-summary-001`，目录名不是功能证明；其当前可确认内容只是辅助汇总，不可直接命名为损失计算器。

## 结果对象的范围与两侧含义

`237FC0` 请求分配 `0x138` 字节，再调用 `1DD020` 初始化。后者在结果对象 `+0x10` 和 `+0x88` 放置两个侧对象，并初始化 `+0x100/+0x104/+0x108/+0x110` 及 `+0x118` 文本。构造路径从战斗两侧复制国家引用、文本和若干整数槽，部分槽在复制时除以1000，并把战斗对象 `+0x30` 的指针写入结果对象 `+0x110`。分配大小不能单独成为可安全读取全部字节的运行合同。

第十三批对结果虚表的有界普通 PE 读取找到了保存函数 `1DD240`，侧虚表的对应函数为 `1DCE20`。保存函数使用的键名来自固定编译记录，尚未读取本次运行中的键名向量，故下表只闭合静态默认名称。完整范围、Evidence ID、请求与运行守卫见[本批研究索引](../../../work/runtime/information-battle-layout-20261025-001/research-index-001.json)，编译记录字节见[结果键](../../../work/runtime/information-battle-layout-20261025-001/result-save-keys-001.json)和[侧键](../../../work/runtime/information-battle-layout-20261025-001/side-save-keys-001.json)。

| 对象与偏移 | 保存函数中的默认键或用途 | 仍需核对 |
| --- | --- | --- |
| 结果 `+0x118` | `name` | 编码与战斗名称生成规则 |
| 结果 `+0x110` 所指对象的 `+0x20` | `location` | 对象寿命、合法省份及地点类型 |
| 结果 `+0x108` | `result`，输出 `yes/no` | 真值对应哪一侧、重排分支 |
| 结果 `+0x10/+0x88` | `attacker/defender` 侧对象 | 与原始战斗侧、战争侧的对应 |
| 结果 `+0x104/+0x100` | `winner_alliance/loser_alliance` | 联盟汇总的业务含义，不能当兵力或损失 |
| 每侧 `+0x10/+0x18` | `country/commander` | 国家编码、指挥官字符串的来源和有效期 |
| 每侧 `+0x38/+0x3C/+0x40` | `infantry/cavalry/artillery` | 数量尺度、初始或剩余含义 |
| 每侧 `+0x44/+0x48/+0x4C/+0x50` | `heavy_ship/light_ship/galley/transport` | 数量尺度、俘获与剩余的区分 |
| 每侧 `+0x54/+0x74` | `losses/war_goal` | 损失单位、战争目标贡献含义 |

`1DD930` 会重置 `+0x100/+0x104`，按国家引用、胜负标志和战争成员重新累加辅助值；这两个槽因此不能据位置或当前数值猜成双方伤亡。曾误选的 `1DCB10` 已在索引中标为 `selection_error`，不作为侧保存函数的证据。陆战格式器的[机械字段账本](../../../work/runtime/information-battle-layout-20261025-001/land-message-field-ledger-001.json)另记有12个栈汇总偏移、结果胜负与动态侧偏移，以及20组我方/敌方兵种模板键；账本保留分支、别名和尺度未决条件，不直接转成公开字段。

存在战争上下文时，构造路径按参与方是否属于战争一侧决定是否交换结果对象两侧的数据。交换内容包括国家引用、文本、部分数值槽和布尔标志；布尔标志的完整胜负约定仍待核对。因此至少要分别保存：

- 战斗原始两侧及其参与者；
- 战争阵营与结果对象重排后的两侧；
- 通知格式器按当前游戏观察对象选择的“我方/敌方”。

当前游戏玩家与信息服务观察国家曾分别为POR和FRA。消息格式器使用游戏全局观察对象，不能据其“我方”字段直接认定FRA视角，也不能把战争阵营无条件称为战斗进攻方或防守方。

## 消息键与字段账本

第十四批继续核对了数值写出与界面显示，见[数量研究索引](../../../work/runtime/information-battle-scalar-writers-20261025-001/research-index-001.json)和[来源审计](../../../work/runtime/information-battle-scalar-writers-20261025-001/source-audit-001.json)。这三条新REA仍绑定同一1.37.4 EXE，只读复用完成缓存，没有调用游戏函数。

| 路径 | 静态证据证明的内容 | 不能据此推出 |
| --- | --- | --- |
| `1707B30`，97字节 | 第三个参数的4字节值交给格式器；普通PE在RVA `1D648D8`窄读证实格式为`%d\0` | 整数对应兵力、舰船还是战争目标贡献，以及初始或剩余口径 |
| `CFCD0..CFCE1`，18字节 | 从有符号int指针读取并执行整数除以1000 | 可以先相减再转换，或可用浮点四舍五入替代 |
| `AE8A80`，7段共1355字节 | 按`int(float(value) * (float(scale)/1000.0))`取得显示整数，再选整数、分组或缩写形式 | 已获得真实界面文本、完整本地化或所有边界值的运行结果 |

侧保存函数的汇编还闭合了8个`R8d`读取与保存键的实际调用，弥补反编译器省略第三参数的问题；`losses`槽直接使用同一整数字符串格式器。读取表达式和普通PE格式字节分别记录在[写出账本](../../../work/runtime/information-battle-scalar-writers-20261025-001/scalar-field-writer-001.json)。保存值、界面显示值和结构化原始数量需要分别保存，不能把显示缩写反推为精确值。

陆战模板的初始数量来自原combat侧的`+0x118/+0x11C/+0x120`，损失来自`+0x134/+0x138/+0x13C`。各值先经`CFCD0`转换；剩余数量使用转换后的初始值减去转换后的损失值。不能改写为对原始差值只除一次。海战模板使用带符号损失累加器与转换后初始值相加，机械账本未观察到可直接套用陆战减法的相同表达式。完整陆战20条、海战24条模板及顶部侧别名分支见[单位显示账本](../../../work/runtime/information-battle-layout-20261025-001/unit-display-ledger-001.json)。`OUR/ENEMY`仍是游戏观察对象的视角，不能直接标成FRA。

在所观察的调用中，`AE8A80`的scale为1000：小于1000时写整数；1000至99999按逗号分组并将余数补足三位；达到100000时写整千加`k`。补零字符串`00/0`有单独的有界PE字节证明，后缀`k`来自REA中的内联字符。这解释了为什么显示文本可能省略精确数量，但仍未验证实际界面、本地化和极端边界值。完整战报文本仍需从有效的原生格式化结果取得。

普通固定PE字节调查发现 `LANDBATTLEOVER` 和 `NAVALBATTLEOVER` 各一个精确ASCII字符串，并验证四条候选引用的指令边界。合计只解码两个指定 unwind 范围的32992字节，没有整映像反汇编，见[通知键引用](../../../work/runtime/information-battles-20261025-001/message-key-xrefs-001.json)。这类普通文件证据与REA函数结果分别保存。

海战格式器 `22E6B0` 的选定伪代码把多个读取表达式用于 `OURPRESTIGE`、`OURTRADITION`、`OUREXHAUSTION`、`SHIPS` 等模板键；另有 `WARSCORE_FROM_BATTLE` 的有符号组合。机械账本记录了栈上汇总对象的12个偏移，以及结果对象 `+0x84/+0xFC` 的读取位置、原表达式、伪代码行号和附近模板键，见[字段账本](../../../work/runtime/information-battles-20261025-001/naval-message-field-ledger-001.json)。这些关联还没有闭合全部类型、尺度、初始/损失/剩余含义，不能直接发布为统一字段映射。

实际 `interface/end_of_combat.gui` 定义了陆战、紧凑陆战和海战三个结果窗口，包含双方盾牌、指挥官、胜负、数值展示槽和俘获舰船控件。三个窗口名在EXE中存在，但本次针对LEA/MOV的RIP字节模式没有找到直接引用；这一有限负结果不证明没有引用。GUI中也没有声明事件编号、战争编号、顺序、去重或断档语义。来源与行号见[GUI调查](../../../work/runtime/information-battles-20261025-001/battle-stage/gui-source-survey-001.json)和[字面定位](../../../work/runtime/information-battles-20261025-001/gui-key-xrefs-001.json)。

## 为什么不能把这些函数用作只读查询

路由会写一次性状态并继续游戏结果处理，构造器会分配对象，`238620` 包含国家临时变量的写入与后续回调，消息格式器会生成通知。这些路径都不是已经证明无副作用的查询入口。当前没有主动调用这些战报函数，也没有安装战报钩子或新增脚本采集。为国内压力验收恢复的 v22 信息观察器不包含本批战报队列。

路由在部分条件下紧接着释放结果对象，栈上汇总值也只在这次调用中有效。由此可以推断，将对象地址交给外部程序稍后轮询存在失效风险。未来采集需要先完成线程、位置、对象寿命和复制预算审计，在有效期内复制必要原始内容，再把稳定数据交给去重、订阅与输出路径。静态定位本身不授权安装或派发。

## 脚本回调的线索与限制

当前安装的基础 on_actions 文件明确包含国家、单位和省份层级的战斗胜负入口；基础 `on_battle_ended_effect` 使用 `land_units_killed/lost` 和 `naval_units_killed/lost` 更新累计变量。原生 `238620` 中也观察到这四个名称的临时写入和后续处理，因此脚本回调值得继续追踪。

但原生枚举与脚本入口的对应尚未闭合。启用栈还包含补充模组及 `llm_bridge`；当前静态加载器只确认文件和启用顺序，没有证明 on_actions 重复定义的引擎合并规则。独立调查因此将实际生效来源保留为未知，见[脚本来源调查](../../../work/runtime/information-battles-20261025-001/battle-stage/on-action-source-survey-001.json)。已有累计变量也没有逐场事件编号、战争编号、初始/剩余兵力或完整载荷，不能改名后当作B01–B04采集结果。

## 大证据文件的读取边界

首个 `22E6B0` 查询写出了10577723字节的REA文件，随后本地读取器因10 MiB上限退出1，尚未生成 `run.json`。本轮没有重复该查询、调高通用上限或把整文件读入PowerShell数组；改用mmap扫描JSON跨度，每个选定值最多2 MiB。选定的身份、profile、函数范围、伪代码及调用关系均已解析，原始文件SHA和数据库前后承诺也已独立核对。

这份[恢复报告](../../../work/runtime/information-battles-20261025-001/rea-message-dispatch-001/readback-recovery-001.json)只证明选定值和相关身份检查，不声称重新验证了整份JSON语法，也不补造缺失的provider退出码或内存峰值。其余五次查询分别保留正常 `run.json`；全部只读复用固定SHA的完成缓存，未重新分析工程。证据类型、恢复限制与运行观察必须继续分开。

第十三批陆战REA原文件为10,281,549字节，大于十进制10 MB、小于10 MiB；旧机械账本中的“>10 MiB”注释不准确。第十四批以独立errata保留这个区别，未修改旧artifact，也未为读取该大文件放大全局预算。

## 已实现的复制队列

[information-battle-buffer.h](../../../work/native/information-battle-buffer.h) 为未来自然战斗结果回调提供固定内存的传递组件：一个生产线程在对象有效期内复制字节，一个消费线程按顺序取出自己的副本。队列有64个槽，每条最多4096字节，不保留源指针；队满时保留旧记录，拒绝新记录并计数。空输入、空指针、超限和过期身份分别记录拒绝原因。

记录使用安装身份、递增世界代际与尝试序号。有效身份中的失败尝试也占用序号，后续记录可显露缺口；即使最后一次尝试被丢弃，也能从统计中的最后尝试序号发现尾部缺口。一个队列对象永久绑定首次有效安装身份，只能在生产者和消费者均停止、队列为空时重置为更大的代际；切换安装须新建队列，避免回到旧身份后重复编号。统计的多字段快照明确为 `consistent=false`，不能当同一时刻的精确元组。

独立[原生测试](../../../work/native/tests/information-battle-buffer-test.cpp)验证了复制后源数据可变、满队列不覆盖、FIFO与缺口、输入边界、A→B→A身份重用拒绝，以及双线程校验和与计数。现有 MinGW 13.2.0 严格警告构建和实际运行均退出0，见[测试报告](../../../work/runtime/information-battle-layout-20261025-001/native-buffer-test-001/report.json)。当前工具链缺少 `libasan/libubsan`，未取得 sanitizer 结果。队列没有游戏地址、钩子、原生函数调用、分配或I/O；这些测试不证明真实战报已被捕获。

## 进入生产前的缺项

还需逐项闭合两侧重排、数量和损失的单位、战争及战斗身份、日期与地点、指挥官、俘获和撤退/全歼含义、回调覆盖范围及实际可见性。随后还要审计自然结果钩子的ABI和生命周期，将有效期内的必要字段复制到队列，完成帧回调排出、持久化、去重及订阅交付，并用真实陆海战逐字段核对B01–B04。队列中的序号和统计只是其中一层，不能单独保证从原生回调到外部消费的完整性。
