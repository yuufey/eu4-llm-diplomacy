## 原生窗口分几步形成

已有固定版本REA证据表明，陆战`8c75d0`和海战`8ca460`分别填充多个控件：数量、损失、威望、传统、将领和胜负等都使用各自的输入。之后，原生格式化函数`14b33a0`使用“消息定义键加`_1`”和104字节参数数组生成`Line1`文字，再交给setter。

本轮实际模板仅为`$NAME$`，所以这条路径在当前配置中提供名称行。即使取得这行文字，其他表格控件、胜负、按钮及显示条件仍需分别补齐。不能为了得到一个`Line1`正例，把它称作完整战报正文。

消息定义表的查找路径现已闭合：全局cell RVA`0x242bcd8`指向manager；manager的桶表按键哈希选择链，再比较定义对象`+0x38`的完整String32键。没有命中时，原生函数会进入日志或分配分支。新的只读读取器直接读取已注册记录，遇到缺失或不一致就返回未知，不调用原生查找或其fallback。

定义对象中的三个字段需要与消息实例区分：

| 对象与偏移 | 已有静态证据支持的含义 |
| --- | --- |
| definition `+0x58`，有符号32位 | popup类型；1为陆战，2为海战 |
| definition `+0x5c`，有符号32位 | 陆战布局条件；0选择compact，非0选择detailed |
| definition `+0x60`，单字节 | 选择按钮配置分支；不代表最终控件可见性 |
| message instance `+0x60` | 独立消息对象中的辅助字符串，不能当作上述定义标志 |

`definition+0x58`会变化。首轮实际读取时，两个精确键对应的对象都为0，读取器因预设“陆战必须1、海战必须2”而拒绝输出；原报告已保留。后续构造函数REA确认该字段初始化为0，普通PE证据确认vtable `+0x40`的4字节函数会把参数写入`+0x58`，战报形成前才按陆战或海战写入相应值。因此，键所代表的战斗类型与当前popup类型字段必须分别记录；0不能被当作注册对象无效，也不能用这个当前值推断某场旧战斗的UI路径。

修正后的[第二次只读实采](../../../work/runtime/information-battle-body-source-20261028-001/current-definitions-002.json)已通过。两个定义的当前原值都是`popup_kind_raw=0`、`layout_raw=1`、`button_flag_raw=1`；`formatter_kind`分别为1和2，`matches_formatter_kind=false`。两遍读取、前后代码校验及独立玩家状态核对均一致，进程句柄已关闭。对象的vtable地址与静态类RVA`0x1cc1ec0`相符，但本轮没有调用setter，也没有观察到它在某场战斗中执行。动态字段证据见[修正合同](../../../work/runtime/information-battle-body-source-20261028-001/definition-dynamic-kind-contract-002.json)。

## 实现与验收边界

新增的参数长度计划器根据实际type-2文字值计算上界，保留占位符出现顺序，拒绝缺失替换值、NUL、重复键、别名和越界。`Workspace::build_for_bound_template`将该检查接入既有104字节参数构建流程；现有`build()`和已成功的59字节leaf实验不重放。这些是离线组件验证，不表示已调用正文函数或已生成结果框。
