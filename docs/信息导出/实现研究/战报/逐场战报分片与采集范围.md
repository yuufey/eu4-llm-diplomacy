## 超过4096字节的载荷

[原生分片编码器](../../../work/native/information-battle-fragment.h)将一份完整自有字节载荷切成多条原有Record，不改变旧队列、wire或文件写入器。每条Record内有64字节header及最多4032字节数据，整数为little-endian：

| 偏移 | 字段 | 约束 |
| --- | --- | --- |
| 0 | 8字节magic | `EU4BFRG1` |
| 8、10 | u16 header长度、flags | 64、0 |
| 12 | u64 message_id | 非零；由调用方在同安装、世界代际内避免复用 |
| 20 | u32完整长度 | 1至1048576字节 |
| 24、28 | u32分片索引、总片数 | 索引从0开始；片数为完整长度除4032向上取整 |
| 32、36 | u32本片长度、分片容量 | 本片长度按索引精确计算；容量固定4032 |
| 40 | u32完整载荷CRC32 | IEEE CRC32，供意外损坏检测 |
| 44–63 | 保留字节 | 全零 |

`prepare()`只遍历完整输入一次来计算CRC，生成不含指针的plan。`encode()`先检查plan、长度、索引、容量、地址溢出和别名，再写header和对应数据；失败写入长度为0且不改输出。组件不分配或保存源指针，调用方仍须在所有片编码期间保留不可变的完整自有副本。超过1MiB明确拒绝，不能裁剪后宣称完整。

每片仍有自己的外层传输尝试序号。message_id用于组装，二者不能互换。分片不是原队列的一次原子发布；队列满、捕获失败或部分片未提交时，接收端必须保留缺片状态。1MiB对应261片，大于64槽队列容量，未来自然钩子接线仍需安排完整副本与排出，不能在原始内容消失后依靠游戏指针续传。

## 重组、游标与错误状态

[BattleReassemblyStore](../../../work/information_battle_reassembly.py)只从已提交的BattleTransportStore记录读取，按installation、world generation、message_id隔离组。SQLite启用并核对`synchronous=FULL`，分片、外层尝试证据和接收顺序游标在同一事务中提交；失败后重读原记录。源库路径、文件身份、创建标记和schema绑定会在poll/status核对，schema检查使用只读连接，不会因源文件消失而创建新库。源记录沿用既有接收器的追加与不可变合同。

相同片的重试幂等；不同metadata或同索引不同字节会持久标为conflicted，保留首次字节及冲突证据，不推进失败行的游标。已完成组后来发生冲突，也立即撤销当前`transport_complete`状态，保留历史完整载荷用于审计。CRC错误同样持久锁存，关闭重开后仍可查询。

新组接收和分片分配受64个未完成组、8MiB暂存字节的准入门限约束，容量不足明确停止，不自动淘汰或跳过。已完成消息后来被判冲突时，记录该故障优先于准入门限，因此状态中未完成组数可能超过门限；这不允许继续准入或隐藏故障。每轮最多256条源记录，列表最多256组，每组缺片索引最多261项。载荷只由显式`get_message()`返回，最多1MiB；正常列表不携带完整字节。

收齐所有规范索引、总长度和CRC通过后，重组器保存完整载荷及SHA-256，并只标记该组`transport_complete=true`。`battle_complete`和`overall_complete`始终false；收齐字节不证明它们已覆盖真实结果框、可见范围或全部战报。

[原生测试](../../../work/runtime/information-battle-fragments-20261025-001/native-fragment-test-001/report.json)以严格C++17、禁用异常构建运行，实际组合既有queue、drain、wire、checked writer输出日志。1、4032、4033、10037、1048576字节五份测试载荷产生268条独立Record，再重复一次原Record模拟确认丢失，共269帧；原生日志为2235247字节，SHA为`6eef49d60293938c01f090c4a33203627b4059190b971f6cabe324cd81104092`。

[Python最终验收](../../../work/runtime/information-battle-fragments-20261025-001/python-reassembly-test-001/report-002.json)经真实tailer→transport→reassembly读取日志，重组五条消息并逐字节核对，13 passed、4 subtests、0 skipped。另覆盖乱序、重启、冲突和CRC锁存、容量停止、源库替换、只读检查竞态、提交失败和游标比较更新。旧报告001保留。

## 文本与自然入口的边界

`14B33A0`使用精确的“先乘`0x1000193`、再XOR字符”递推查本地化表，缺模板时会复制输入key。命中后使用栈缓冲区，寻找成对`$`并调用`14B2B40`展开参数。展开后检查目标偏移是否超过`0xFC00`；相应分支重新初始化输出对象，再从当前scratch输入复制，尚不能据此声称返回空串或完整无截断文本。参数展开、编码、合法线程和生命周期仍待核对。

账本另核对244630的16字节普通PE入口窗口`[244630,244640)`及四条完整指令：保存RDX、push RBX、分配栈、将RDX移入RBX。后续机器参数表明RCX为manager、RDX为message、R8/R9构成可选对。这里只定位静态候选边界；没有安装钩子，也未证明unwind、重入、线程或观察范围。不能主动再次执行这些路径获取战报。

下一最小来源问题是路由23A020在参与者回调前有条件调用`1DD3C0`及`D89A80`，后者已有181B函数边界。需要继续核对其是否保留结果及关联战争，并与结果条件释放路径对照；当前没有将该候选解释为已证明的历史所有者。
