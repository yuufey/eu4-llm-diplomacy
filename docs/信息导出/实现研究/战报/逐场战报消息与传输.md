## 模板、消息与窗口是不同对象

原生分析固定为EU4 1.37.4，EXE SHA-256为 `b23fa0e1f698d31b01cdd1c3817a675805d8c6286cb66f9c231e6e2a42544d77`，静态基址为 `0x140000000`。下表使用RVA；完整静态VA、包含端点的多段函数体、Evidence ID及查询进程关闭记录见[研究索引](../../../work/runtime/information-battle-message-20261025-001/research-index-001.json)。普通PE虚表窗口单独记录，不作为REA或运行观察。

| 函数RVA | 本批静态观察 |
| --- | --- |
| `8D44A0` | 将模板参数容器移入消息对象，清空原容器，并记录游戏日期；未在这里形成完整连续文本 |
| `244630`、`1AF380` | 提交时再次移动消息，然后清理原对象；旧容器地址不能作为延迟读取依据 |
| `8C05F0` | 按游戏、消息管理器及通知配置分支处理，可能直接清理，也可能生成通知、窗口或日志 |
| `8D4660` | 使用消息键加 `_LOG` 形成带日期的日志文本，与完整结果框内容不同 |
| `8C1270` | 明确选择陆战、紧凑陆战或海战结果窗口 |
| `8C1DC0` | 将消息传入窗口内部对象，再调用陆战或海战填充函数；内部复制方式尚待核对 |

陆海战格式器末尾的 `local_res8` 会被消息管理器 getter 的返回值覆盖。因此它在最终提交调用中已不再是早先的战斗对象别名。提交函数的伪代码还省略了移动构造器的第二参数；本批用实际寄存器传递和独立移动构造器证据补足这一点。具体表达式、指令位置及限制见[消息有效期账本](../../../work/runtime/information-battle-message-20261025-001/message-lifetime-ledger-001.json)。

这些观察说明了为什么不能只保存一个消息指针，也不能把原生日志当作完整战报。消息可能在多个阶段移动或清理；部分通知开关会使后续路径不发生。下一步需要核对 `598DC0` 的消息复制方式，以及 `8C75D0`、`8CA460` 怎样填写真实陆海战窗口。合法读取范围、回调重入、观察方可见性和原文完整性仍未取得运行证据。

## 通用记录怎样传输

[原生编码器](../../../work/native/information-battle-wire.h)接收队列中的自有字节副本，生成一条JSONL。它不解释载荷，也不证明其中没有指针或已经包含完整战报。字段如下：

| 字段 | 格式与含义 |
| --- | --- |
| `event`、`wire_version` | 固定为 `information_owned_battle_record` 和整数1，仅表示传输格式 |
| `installation`、`world_generation` | 非零、16位小写十六进制字符串，区分安装与世界代际 |
| `attempt_sequence` | 无前导零的十进制字符串，完整保留64位无符号序号 |
| `payload_encoding`、`payload_bytes`、`payload_hex` | `hex`、1至4096的字节数，以及长度严格匹配的小写十六进制内容 |

编码器不分配内部内存。它在写入前验证身份、长度、输出容量、地址计算溢出及输入输出重叠；失败时返回错误和零写入长度，保留原记录。成功结果包括末尾换行，另写一个不计入长度的NUL。发送端字段顺序固定；接收端按字段和类型校验，拒绝未知或重复键、非法UTF-8、非有限数值和不完整帧。

单条4096字节是当前传输组件的上限，不是完整战报的大小假设。分片和组装尚未实现，未来不能把超限内容裁剪后称为完整结果。

## 接收确认与持久化

[Python接收器](../../../work/information_battle_transport.py)先检查输入预算再复制和解析，把原始wire、载荷、SHA-256及安装/代际/序号写入SQLite。序号使用TEXT存储，避免超过SQLite有符号整数范围后丢失精度。文件数据库显式启用并核对 `synchronous=FULL`；只有事务提交返回后才确认新记录。内存数据库只用于临时使用，不提供磁盘保存。

相同身份和序号、相同载荷的重试返回幂等确认，保留首次收到的wire；相同身份和序号却有不同载荷时拒绝覆盖。事务失败不确认，重试仍可使用原编号。这是接收保存阶段的确认，不等于信息事件已生成、LLM已阅读或游戏中的战报采集完整。

接收器分别保存历史上观察到的序号缺口和当前仍未收到的区间。后到记录会拆分或填补开放区间，历史观察仍保留；即使当前没有开放区间，也保持 `complete=false`，因为尚未证明采集开始前和最后一条之后没有遗漏。区间用边界表示，不枚举可能达到 `UINT64_MAX` 的缺失序号。

记录查询按接收顺序分页，默认256条、最多1024条。缺口状态也有页数上限，并返回总数与截断标志；多个状态查询在同一SQLite读事务中取得一致快照。接收顺序和原生尝试序号分别保存，不将乱序到达改写成原始产生顺序。

## 本批验证及接入边界

[编码器最终报告](../../../work/runtime/information-battle-message-20261025-001/native-wire-test-001/report-002.json)记录严格C++17与禁用异常的构建运行，覆盖容量差1、身份/序号边界、全字节载荷、重叠拒绝和确定性重试。两个真实原生向量包含4096字节及 `UINT64_MAX` 的边界，并由Python全部解析保存。

[组合测试](../../../work/runtime/information-battle-message-20261025-001/native-handoff-test-001/report.json)实际使用原有队列排出组件和新编码器写出三行：A首次完整写出但故意不确认，再次写出相同A并确认，最后写出4096字节的B。[Python最终验收](../../../work/runtime/information-battle-message-20261025-001/python-transport-test-001/report-004.json)读取全部三行，确认数据库最终只有两条记录，关闭重开后原始wire和载荷相同；共19项测试及24个subtests通过，无跳过。这里模拟的是确认丢失，未模拟磁盘断电或证明原生写入器的崩溃恢复。

当前观察器的旧 `line()` 返回void，未把文件写入和刷新结果交给调用方，不能直接当作新排出组件的确认接口。正式接入还需处理实际写入失败和半条记录、持久游标、分片与重组，再连接真实战报采集及信息事件源。新组件全部保存在 `work` 下，没有改变生产目录、已安装DLL或既有外交权限。
