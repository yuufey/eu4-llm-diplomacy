# 信息导出与统一操控接口更新说明

EU4 1.37.4 的统一服务向 LLM 提供信息查询、报告、订阅和外交操作。服务通过 MCP stdio 或诊断用 JSONL 接收工具调用；同一连接共享信息来源、游戏会话和外交请求账本。MCP 是默认入口。服务启动时注册 9 个信息工具和 4 个外交工具。

## 可以查询哪些信息

信息目录按当前连接实际可用的主题、字段、国家范围和来源报告能力。LLM 应先调用 `information_discover`，再依据返回的目录选择查询；不同安装、版本和来源可能提供不同字段。

当前信息覆盖大致包括：

| 范围 | 信息示例 |
| --- | --- |
| 国家与国内状况 | 财政、人力与军力、点数、稳定度、修正、任务和国内压力 |
| 外交与国家关系 | 好感、关系、宿敌、宗属、保证、宣战候选、参战意愿及外交义务 |
| 领土与世界信息 | 省份归属、核心与宣称、领土兴趣、贸易节点及贸易信息 |
| 战争与事件 | 战争状态、参战方和战争领袖、战报，以及来源支持的外交提议和生命周期事件 |
| 宗教、政府与国际组织 | 宗教资料、政府状态、神圣罗马帝国及其他已接入的专题信息 |

这是一份能力概览，不代表每个连接都能读取表中所有内容。主题和字段的精确清单以 `information_discover` 返回值为准。未取得、不可见、不适用和暂时不可用会分别标记；数值 `0` 与 `false` 是有效结果，不能当成未知值。

## 按需查询和复用报告

LLM 可以主动读取一次信息，也可以先保存查询组合，再按报告编号读取。每个查询使用主题 `topic` 和对象 `object`；`fields` 与 `parameters` 可选，省略时服务按主题目录展开。`information_query` 需要稳定的 `request_id`，并且必须且只能提供 `queries` 或 `report_id` 其中之一。

下面是一次读取法国财政信息的 JSONL 工具请求：

```json
{"tool":"information_query","arguments":{"request_id":"finance-read-001","queries":[{"topic":"N01","object":{"type":"country","country":"FRA"},"fields":["treasury","monthly_income","monthly_expenses","monthly_balance","loans"]}]}}
```

下面的输出摘自现有简洁视图示例，数值只用于说明结果结构，不代表当前游戏状态。每个 `items` 条目对应一个查询对象；`information_get_result` 可按 `result_id` 读取完整来源与诊断记录。

```json
{
  "result_id": "result-4140c10d879c4dac9e53c6abf13c4fd0",
  "items": [{
    "country": "FRA",
    "treasury": 84.730,
    "previous_month_recurring": {"income": 29.198, "expenses": 31.253, "balance": -2.055},
    "loans": {"count": 4, "principal": 512}
  }]
}
```

查询和结果回读默认采用面向 LLM 的简洁业务值；需要检查来源、完整性和诊断时可指定 `view: "full"`。可复用报告通过 `information_manage_report` 创建、修改或删除；修改时要提交完整配置和当前 `expected_version`。

## 定期报告和自主订阅

LLM 可以创建报告，再让服务按时间周期、采样变化或来源事件运行该报告。订阅引用 `report_id`，不会复制报告内容；订阅暂停、恢复或取消时，也不会关闭其他订阅共用的数据来源。

以下两条请求展示完整的报告与周期订阅参数。第一步返回的实际 `report.id` 必须复制到第二步的 `report_id`。代码块中的 `report-id-from-create-response` 是说明占位符，不是已存在的报告编号。

第一步创建 FRA 的点数周报：

```json
{"tool":"information_manage_report","arguments":{"request_id":"report-create-weekly-001","operation":"create","config":{"name":"FRA 点数周报","queries":[{"topic":"N06","object":{"type":"country","country":"FRA"},"fields":["monarch_points"],"parameters":{}}],"detail":"brief"}}}
```

第二步每经过 7 个**游戏日**生成一次报告：

```json
{"tool":"information_manage_subscription","arguments":{"request_id":"subscription-create-weekly-001","operation":"create","config":{"name":"FRA 每 7 个游戏日报告","kind":"periodic","report_id":"report-id-from-create-response","enabled":true,"schedule":{"basis":"game","every":7,"unit":"days","missed":"coalesce"}}}}
```

如果 LLM 需要在收到提议时查看当前事务，可以按第一步的方法创建内容为 `C03.pending_matters` 的报告，再用它的实际编号创建事件订阅。下面只匹配萨伏依发给法国的外交提议；`report-id-for-pending-matters` 同样需要替换为实际报告编号。

```json
{"tool":"information_manage_subscription","arguments":{"request_id":"subscription-create-proposal-001","operation":"create","config":{"name":"萨伏依对法国的外交提议","kind":"event","report_id":"report-id-for-pending-matters","enabled":true,"event":{"types":["diplomatic_proposal"],"actors":["SAV"],"recipients":["FRA"]}}}}
```

该订阅在来源交付符合筛选条件的事件后生成报告，不使用 `schedule`。若希望按采样发现内容变化后再生成报告，可配置 `kind: "change"` 并提供完整 `schedule`；它能观察的变化取决于来源能力和采样频率。

`schedule.basis` 决定周期使用哪一种时钟：`{"basis":"game","unit":"days"}` 按游戏日期计算，`{"basis":"real","unit":"seconds"}` 按现实秒数计算。`every` 是对应时钟中的间隔；示例的 `every: 7` 表示七个游戏日，不是现实中的七天。游戏暂停时，游戏日期不前进，游戏日订阅也不会因此到期。省略 `binding` 时，服务使用当前来源的会话、观察方和版本；如需固定身份，应使用 `information_discover` 返回的当前值完整填写 `binding`。

服务需要持续轮询才能自动发现到期周期和新事件。MCP stdio 模式在客户端初始化后，只有设置 `--tick-seconds` 为正数才会启动后台调度循环；该值是**现实秒数的轮询间隔**，不是订阅周期。JSONL 模式没有后台循环，调用方需要定期调用 `information_tick`。每次 `information_tick` 只运行一轮到期调度和事件匹配：它不推进游戏日期、不执行外交行动，也不会替代持续运行的后台进程。游戏事件订阅同样依赖来源轮询，并且只能匹配来源实际支持的事件类型。

调度生成的报告会保存在信息服务中。LLM 或宿主可再调用 `information_status`、`information_list_results` 和 `information_get_result` 检查订阅状态、结果及交付状态；创建订阅本身不会把结果直接插入任意 LLM 对话。订阅类型、事件筛选和结果状态的字段说明见[信息接口使用说明](../信息导出/接口/信息接口使用说明.md)。

## 外交查询与实际操作

4 个外交工具分别提供行动目录、方案预览、执行和结果回读。先用 `list_diplomatic_actions` 或 `inspect_diplomatic_action` 查询当前条件，再用 `execute_diplomatic_action` 提交唯一的 `request_id`，最后用 `get_diplomatic_result` 按原编号读取结果。执行可能改变实际游戏状态；结果不确定时，应继续查询原请求，不要换新编号重复提交。操作后还可以用信息查询复查受影响状态。

下面的请求及输出摘录来自英国（ENG）改善与萨伏依（SAV）关系的一次真实执行。请求字段符合 `execute_diplomatic_action` schema；输出摘录省略了回执中的日期、原生证据和其他字段。这是历史请求编号，不应重发；新操作应生成新的唯一编号。

```json
{"tool":"execute_diplomatic_action","arguments":{"request_id":"country_scope_eng_sav_improve_20261116_001","action_id":"improve_relations","actor":"ENG","recipient":"SAV","phase":"initiate","parameters":{}}}
```

```json
{
  "request_id": "country_scope_eng_sav_improve_20261116_001",
  "status": "executed",
  "submitted": true,
  "game_outcome": "executed",
  "result": {
    "action_id": "improve_relations",
    "actor": "ENG",
    "recipient": "SAV",
    "phase": "initiate",
    "task_before": false,
    "task_after": true,
    "execution_verified": true
  }
}
```

## 操作者配置的身份和权限

操作者在启动服务时为每个 LLM 连接配置身份和控制国；模型的工具参数不接受客户端自行指定权限。

- `--owner` 是操作者分配的调用方身份，也用作信息数据命名空间，并记录在外交请求中。请求归属检查会阻止另一个身份读取或重用不属于它的外交请求。
- `--controlled-country` 指定该连接可以代表哪个国家作外交决定。省略时沿用 `--observer`；两者都省略时，该连接没有外交执行权限。主动发起或撤回按 `actor` 检查；接受或拒绝入站提议按实际作出回应的 `recipient` 检查。
- `--managed-countries` 指定同一游戏进程中由原生 DLL 接管的国家集合，最多 32 个国家。它约束原生自动外交拦截范围，不会自动授予某个 LLM 代表集合内每个国家行动的权限。每个连接仍需单独配置 `--controlled-country`，DLL 确认集合后服务才开放相应操作。

例如，操作者可以为英国模型配置 `--owner england-agent --observer ENG --controlled-country ENG --managed-countries ENG FRA`。如多个模型共用游戏进程，应向它们配置相同的 `--managed-countries`，再分别设置身份和控制国。启动、连接及其他来源参数见[统一游戏服务使用说明](统一游戏服务使用说明.md)。

外交权限与信息可知范围是两套检查。`--controlled-country` 授权外交决定，不代表信息适配器已经按该国完整隔离所有外国字段。信息查询仍受 `information_discover` 所列来源、观察方和字段能力约束；部分来源对外国国家的可知范围尚未完整隔离。某字段可查询不等于游戏内该国必然知道该信息，也不应仅凭控制国配置推断外国信息权限。
