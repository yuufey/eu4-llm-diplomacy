# 日志、文档与工作区维护

## 文件职责

| 位置 | 内容与更新方式 |
| --- | --- |
| 各级README | 项目或模块介绍。按用户要求，本次及后续进度维护均不修改 |
| docs下的需求、计划、接口和验收文档 | 目标、范围、合同、使用方法、设计依据、验收标准。功能或规则改变时修改相关段落 |
| logs/CURRENT.md | 唯一当前执行状态，覆盖更新，包含最近已交付能力、实际缺项、必要现场身份及下一交付 |
| logs下的历史记录 | 单次交付的简短经过、失败原因、结果与证据链接，按日期或交付组织 |
| work/runtime | 大型原始证据、运行输出、临时数据库、构建产物和监控结果，沿既有本地保存与忽略规则 |
| HANDOFF、PLAN、VALIDATION入口 | 指向对应状态、规范和归档，避免重复维护进度正文 |

历史README中已有的状态文字作为原有内容保留。代理启动时读取logs/CURRENT.md，历史README中的“下一步”不再承担当前调度职责。

接口说明可以引用真实证据解释能力及限制，复盘可以讨论方法与原因。连续追加的批次经过、测试计数、临时现场和下一轮安排属于日志。已有历史研究材料按其性质保留，不能因为带日期就全部移动。

日志记录一次即可。CURRENT只摘取下一次工作必需的结果，其余引用日志或原始收据。文档中的稳定契约有变化才更新对应段落。历史原文归档时保持内容并重定位相对链接，原始路径可保留导航页。

## 减少重复成本

| 重复成本 | 具体处理 | 完成判断 |
| --- | --- | --- |
| 每轮重新理解长交接、复制计划与README | 启动读CURRENT，按当前任务查一份接口合同及对应收据；运行结果只归档一次 | 下一开发者能直接确定观察国、入口、缺项及下一动作 |
| 每个小变化重新写查询、订阅、重开脚本 | 优先调用已有公共API及已经成功的夹具；临时目录固定在工作区，分页按接口合同消费 | 同类任务主要改变输入和断言，而非复制整个运行器 |
| 所有字段都重新演示完整流水线 | 根据改变的合同选测试。字段语义改动验证该字段与相关公开入口；调度器改动才扩大到恢复、取消和跨订阅 | 新增或重跑检查能够对应一项实际风险 |
| 每个来源都升级整套DLL与资产 | 只在兼容的接口组内合并变更；先明确Hook入口所有权，再一次构建、绑定与部署 | 避免同一物理入口重复patch，版本资产有一次可追溯生成路径 |
| REA启动和初始化反复超限 | 使用已保存证据、已知函数边界和窄范围分析；重新使用重工具须有新的具体问题与可执行的资源方案 | 得到能改变实现的结果，或明确结束本次假设 |
| 为等待稀有事件长期空跑 | 针对已知期限或具体变化设观察条件；无正例时区分实现已测与实机证据缺失 | 得到目标即收尾，等待期间不反复查询无关字段 |
| 报告每次重复解析大量对象 | 国家摘要先返回，具体外交比较再展开；缓存身份、失效条件和观测时间清晰 | 对同一场景测查询时间、输出大小及模型实际需要的信息 |

复用顺序是先直接调用现成工具，再调整现有夹具，最后才考虑抽取共享辅助代码。仅因两个脚本相似就构建通用框架，会引入新的维护成本。资源监控继续用于确有内存风险的分析及长任务，纯文档更改以链接和内容核对结束。

## Pylance与编辑器扫描范围

Pylance需要发现和分析Python文件。长期在源码工作区累积每批次的脚本副本、冻结源码、测试临时目录和依赖，会扩大扫描范围。`python.analysis.exclude`约束分析范围，被活动源码导入的排除文件仍可能参与分析。Git忽略规则、文件监听排除和Python分析排除分别解决不同问题。[Python设置说明](https://code.visualstudio.com/docs/python/settings-reference)

工作区设置排除work/runtime、backup、deps、publication、dist、构建输出、日志和缓存的主动分析，保留bridge、tools、tests以及work中的有效源码。文件监听和默认搜索同步排除生成目录。需要查看原始证据时仍可明确打开对应路径，Python运行与pytest收集使用各自的规则。

## 产物留存与清理

根pytest配置将默认收集范围限制为bridge/tests和tests。通过用例的tmp_path在结束时删除，失败用例的临时文件保留，pytest自动编号的基目录只保留最近一轮。显式指定basetemp时，失败目录和通过tmp_path_factory创建的共享目录仍需由运行器按用途收尾，不能假定该设置覆盖所有临时产物。

新运行将PYTEST_DEBUG_TEMPROOT指向已存在的work/tmp，让pytest自行生成有锁的编号目录，避免每批分配永久basetemp。证据目录只保存报告和明确需要的文件。旧运行器的basetemp参数按实际使用逐步改为上述方式，当前配置不会自动迁移历史运行器。

测试报告、失败栈、正式实采和固定版本证据放在临时夹具目录之外。用例只复制必要文件，优先使用最小夹具。批次之间复用公共运行器，运行收据记录输入和版本，避免在每轮重新复制整个工具树。

tools/clean_pytest_artifacts.py默认只预览，显式--apply才删除。范围限定为三个既定scratch根中的test_名称加数字目录，至少24小时未改动，跳过含已跟踪文件、重解析点或新文件的树。报告记录每个目标及文件数、字节数。此工具用于已确认的清理任务，不安排定时自动删除实采或存档。

原生日志的辅助诊断默认每次安装限64 MiB，包括普通生命周期、帧心跳和字段读取开始记录。达到预算时写出一次diagnostic_log_budget_exhausted，说明辅助诊断不再完整。提议到期、按编号移除、重检移除及整队清空所需的析构返回记录持续保留，业务事件、控制结果和故障记录继续追加。64 MiB额度用于辅助诊断，control-probe.jsonl还会追加上述必要记录。实现位于work/native/control-probe.cpp，已经加载的旧DLL需升级后生效。日志沿原有偏移继续追加。

历史副本可用tools/deduplicate_frozen_artifacts.py按内容散列合并存储。工具默认预览，只处理既定目录中至少24小时未改动、未被Git跟踪的候选；清单和每次替换记录保存于logs下的指定目录。硬链接保留原路径与内容，但多个路径共享同一份数据，修改前必须复制到新的工作文件；数据库分析也必须先复制再以可写方式打开。合并存储不会减少目录项数量，编辑器排除规则仍需保留。正式源码和活动数据库不得纳入历史副本处理。

后续运行只记录共享脚本路径、源码散列和输入参数。确需冻结源码时每个版本留一份，再由收据引用；不得每批复制整棵工具树。保存恢复点前先复用已存在的同内容存档，仅在确需新的恢复状态时保存。清理是本次明确任务，不新增定时清理或反复保存任务。

测试存档只保留当前开发恢复点、尚未解决问题实际需要的最小复现，以及自动化测试直接读取的固定夹具。已完成测试的中间存档和旧备份可删除，报告与日志足以保存其历史结果；仅被旧报告提及不构成留存理由。不要用硬链接继续保留所有无用存档。个人游玩存档不纳入开发产物清理。

旧大日志可以在支持NTFS压缩的卷上压缩文件本身，保留路径与逻辑内容。正式证据与当前安装按引用保留，过期存档副本和冻结资产的去重需要另外核对其恢复用途与版本绑定。

## Git状态处理

VS Code内置Git扩展限制状态解析条目数，官方当前默认git.statusLimit为10000。达到限制会减少部分编辑器Git功能。Git命令行仍可用于精确路径的查看和提交。实际触发门槛取决于用户安装版本及配置。[Git扩展配置](https://github.com/microsoft/vscode/blob/main/extensions/git/package.json)

处理应先区分三种情况。

1. 未跟踪的生成输出，给精确输出目录补充ignore，避免把业务源码一起隐藏。
2. 已跟踪的生成输出，ignore不会生效。先确认哪些文件属于可重建产物、哪些是必须保存的固定证据，再决定是否仅从索引移除并保留本地文件。[Git忽略规则](https://git-scm.com/docs/gitignore)
3. 大量真实源码和测试改动，需要按可审查的交付分组提交。文档、配置、接口实现与相应测试保持有意义的提交边界，提交后状态数量才会下降。一次性清空暂存区或删除文件会破坏现有工作组织。

提高statusLimit只能扩大编辑器处理范围，也会增加处理成本。应先缩小输出目录扫描并整理真实改动；需要临时完整浏览时，再根据实际条目数设有限额度。工作区设置本次只处理分析、监听和搜索范围。
