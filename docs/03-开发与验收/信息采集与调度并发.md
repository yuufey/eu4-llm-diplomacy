# 信息采集与调度并发

第191批已继续拆分事件轮询和报告读取，新增逐目标持久队列与安全恢复，见[信息事件持久队列与恢复](信息事件持久队列与恢复.md)。以下耗时数据保留第190批的实测范围。

第190批将手动查询、周期订阅和变化订阅中的耗时读取移出配置锁与 SQLite 写事务。后台采集尚未完成时，状态查询和订阅控制可以处理；完成的读取仍要核对原配置，取消、更新或停用后的旧结果不会继续写入和发布。

## 读取与保存的边界

周期或变化采集分三步：

1. 短事务核对订阅、报告、绑定和调度时间，登记本次 `collection.id`，推进 `next_due`。
2. 在配置锁与写事务之外调用原读取器。底层原生查询已经开始后，不强行中断它；取消会使它失去结果发布资格。
3. 再用短事务核对 collection ID、订阅状态和版本、报告版本、全局设置版本及当前绑定。任何一项改变都丢弃旧尝试，不覆盖新调度和变化基线。

状态中的 `runtime.collection` 表示有效的在途尝试。控制操作可移除该标记；`last_attempt` 保留尝试、丢弃或失败的诊断。标记正常结束后会被清除，不能要求整个 runtime 在采集前后保持相同。

变化订阅先对经过上下文检查的样本计算比较值，只有提交检查通过才更新基线。读取失败、上下文失效或控制操作使尝试过期时，既有基线保持。周期到期点仍按原 `coalesce`/`skip` 规则处理。

手动查询先持久记录请求 ID，再在锁外读取并提交结果。重复的成功请求仍返回同一结果和当前交付收据；已登记但中断、没有最终结果的读取返回 `request_outcome_unknown`，不会自动用相同请求 ID 重读。报告在读取期间更新或删除时，原报告请求的已知值会被标为 stale。

## 采集互斥与交付

配置锁不再承担采集互斥。`CollectionLock` 用线程锁和文件数据库旁的 `.collection.lock` 协调同库各服务实例与进程；内存数据库只用线程锁。锁文件很小，保留原文件以避免替换文件带来的竞态，操作系统会在进程退出时释放持有的锁。

同一次有效采集没有结束时，另一次 tick 立即返回 `state=busy`、空 results，不增加一次读取。等待采集锁的查询不持有配置锁。关闭服务时先等待在途读取结束，再关闭来源和数据库。

外部输出仍遵循先登记交付、再执行外部发送、最后写收据的规则。尚未登记为 delivering 的订阅结果会重新核对取消、版本、设置与来源状态；不再有效则记录失败而不发送。已经登记并开始的外部发送不能撤销，未知收据也不会在重启后自动重发。SQLite outbox 的 delivered 仍只证明结果已持久保存，不证明 LLM 已读。

## 已验证的响应时间

实测使用同一暂停中的 EU4 会话、逻辑 FRA NPC、物理 POR，沿用明确的任务候选成本预览，没有提交外交动作。

| 操作 | 第189批观察 | 第190批观察 |
| --- | ---: | ---: |
| 后台采集期间的状态查询 | 约20.47秒 | 本次最慢0.875秒 |
| 短订阅取消 | 约19.83秒 | 本次记录0.000秒，低于计时分辨率 |
| 重叠 tick | 未单独测量 | 约0.015秒，返回 busy |

第190批在短订阅首次读取尚未发布结果时取消它。该读取后来结束，但没有为短订阅保存任何结果；长订阅保持活动并正常交付，值与第189批相同。最后全部订阅取消，服务与读取线程结束，游戏仍保持暂停。

本次只查询 `costs` 字段，手动查询和报告约8.36、8.03秒；上一批为四字段查询，不能据此宣称相同输入的读取速度提高。性能结论针对状态与控制不再等待后台读取。

125个相关测试有通过记录，覆盖真实 Event 阻塞、读取中取消和更新、变化基线、重复请求、同库 tick 互斥、关闭顺序及交付前失效。完整测试集的历史问题未在本批重验，`whole_suite_passed=false` 保持。

## 本批未改变的部分

MCP/JSONL 的同一输入流仍逐条执行普通 RPC；这次实测证明的是后台 tick 运行时的状态与取消响应，不意味着同一连接能抢占一条尚未返回的手动 RPC。

第190批当时尚未拆分事件轮询、事件结果读取和生产者控制；第191批已完成前两项，生产者控制仍沿原锁边界。事件读取的协议验证使用记录来源，不替代实机来源性能验证。字段覆盖保持61 available、256 partial、80 planned，完整74主题397字段及原阶段范围继续开发。
