# 逐场战报格式化容器采集

第三十三批已经取得一条可公开使用的格式化容器路径：自然战斗记录进入 formatter 的 cleanup 之前，观察器复制容器中的原始键值对，并将它们放入 B04 `details.message_template`。主动查询、报告和事件订阅可以读取同一份 payload；键和值的原始字节、出现顺序和重复键都会保留。

这里的容器是消息格式化的输入。它可以提供可读的键值内容，但不等于已经渲染的窗口标题、正文、换行、控件状态或观察者可见性。当前 `full_display_complete`、`runtime_popup_verified` 和 `business_complete` 仍为 `false`。

## 当前可用行为

v4 的 IBOW 基础帧保持不变。已有的 `BTXT` message 扩展保持原始字节兼容；本批新增 formatter container 扩展，版本为 2，公开来源标记为 `formatter_container_before_cleanup`。有该扩展的记录可以返回：

- `pair_count` 及按原顺序排列的键值对；
- 每个键和值的原始十六进制字节，以及逐项 `eu4_escape` 解码结果；
- `message_metadata_present`、`native_date`、原始标志和容器头字段的已知或缺失状态；
- 辅助字符串尚未采集时的 `MESSAGE_METADATA_NOT_CAPTURED` 缺项。

当前实机容器样本的共同状态是 `message_metadata_present=false`、`native_date=null`、`raw_flag_8c`/`raw_flag_8d` 为 `null`，辅助字符串为 `unsupported`。这表示容器键值已经复制成功，同时明确记录了元数据尚未取得；程序不会用空字符串冒充“没有元数据”。

## 容器关联和失败边界

cleanup 入口按战斗类型区分返回地址：陆战使用 RVA `0x236736`，并检查 container 的 `RBP-0x60`；海战使用 RVA `0x232A28`，并检查 `RBP-0x68`。调用者和保存的 RDI 必须属于已登记的 owner。复制使用真实的 24 字节 container 头和已关联的节点；它不会把一个伪造的 0x90 字节（144 字节）message 对象当作 container，也不会在无法关联时创建模板结果。

scope 夹具覆盖了合法陆战/海战容器、错误 owner、错误 formatter caller、错误 container、日期变化、非法头、重复 cleanup，以及 message 扩展优先级。失败样本保留基础 v4 记录，模板扩展被拒绝，指针不会进入 wire。该夹具证明组件的拒绝和投影边界，不证明每个自然战斗都打开可见的消息窗口。

容器 wire 仍受既有 v4、键值数量、单键、单值和 arena 上限约束。缺失扩展是 `unknown` 或明确缺项，不是已知空模板；旧 v2/v3 记录继续沿用兼容路径。同一记录只编码一种模板来源；已遇到匹配的 message 调用时，cleanup 路径不会再回退复制容器，也不会将两个来源拼成一份自称完整的正文。
