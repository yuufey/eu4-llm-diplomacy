# 逐场战报消息模板采集

本文说明当前逐场战报消息模板的采集、传输和公开投影。这里的“模板”是原生消息窗口在格式化前使用的键值输入；它不等于已经渲染完成的窗口标题、正文或观察者可见性结论。

当前工程已经具备 v4 模板的代码路径、离线原生夹具和公开服务投影。第三十二批已将 v26-003 实装到 PID `34612`（session `34612-1dd651a75345a76`）；DLL SHA-256 为 `ba781dce27e35007898974ee05bc0cfcd79527b4b1d697dfbc8026e4abf887ac`，manifest SHA-256 为 `ff58da375aa042d5538a55a2ff76b4ee082623bfcd0873d386f2f0ad80d08cc3`，构建包含 110 个 source。唯一的 35 天自然窗口从 raw date `56556048` 到 `56556888`，最终状态为 paused、speed 0、source disabled；摄取 9 条 v4 记录（8 条陆战、1 条海战），所有 `message_template` 均 absent。自然窗口的 `template_copied`、`template_copy_failures`、`template_ambiguous` 和 `open_message_scopes` 均为 0；这不能推出窗口内没有 message 调用，也不能推出 POR 未参战导致跳过。修正探针后的只读实机预检已通过，未重新安装 DLL。

固定快照 [`snapshot-001.json`](../../../work/runtime/information-battle-text-20261026-001/capture-snapshot/snapshot-001.json) 保留了本次原始日志和 `raw-v4.sqlite3`；数据库 SHA-256 为 `241bf62e21776c6fb8bc22ddb549c6bfb3ddcaf13c4159926c53e2eb57a2b004`。B04 的 `details.message_template` 和 projection 7 已接通，但当前窗口没有 BTXT 输入，因此不能发布模板键值。只读静态 gate 只证明 message 提交存在分支门槛；在 cleanup 函数 RVA `0x1AF740` 调用前采集模板容器的路径尚未实现，不能据此声称有 `raw_text`、完整窗口正文或 `full_display`。

## 第三十二批实际窗口与公开消费

公开消费验证了两种边界。recorded ATJ 的 seq1 记录为 ATJ/KED/JMB 对 MLC，B04 报告、主动查询和订阅使用同一 payload，模板返回 `unknown`，reason 为 `MESSAGE_TEMPLATE_CAPTURE_UNAVAILABLE`；一次事件在下一 tick 产生 0 条重复结果，服务正常退出。该记录属于 recorded foreign authority，不能当作 live ATJ 证据。当前 live FRA 上下文日期为 raw `56556888`，9 条记录中没有 FRA 直接参战记录，因此 seq1 查询为 unavailable、订阅为 `0→0`；outbox 的 `delivered` 只表示保存了交付记录，不能解释为战报事件已经交付。

模板字段的可用性仍以有 BTXT 扩展的 v4 记录为前提：缺失扩展保持 `unknown`，不会伪造空模板；原始键值和 `eu4_escape` 解码路径已连接，但 `full_display_complete`、`runtime_popup_verified`、`native_visibility_verified` 和 `business_complete` 仍为未完成状态。歼灭、撤退及完整窗口文本仍需独立来源，不能由本次 absent 结果推断。

## 当前能读取的内容

消息记录继续使用 `IBOW` 基础帧。v4 在未改变 v3 基础帧的前提下，附加一个 `BTXT` 扩展块。扩展块保存消息日期、两个原始标志、原始头字段、辅助字符串，以及按原顺序排列的键值对。键和值均先保留原始字节；公开投影随后分别使用 `eu4_escape` 解码，不把多个值拼成一段自称完整的文本。

`bridge/information/battles.py` 将投影放在 `payload.battle_fields.details.message_template`。每个键值项包含 `key_raw_hex`、`value_raw_hex`、顺序索引和各自的解码状态，因此重复键仍按出现顺序保留。某一项解码失败时，该项变为 `unknown`，原始十六进制字节仍保留；失败不会把同一条消息的其他项改成空值。消息日期与结果日期不一致时，整个模板投影为 `unknown`，不使用过期值。

示例只表示接口形状，不是实机返回：

```json
{
  "details": {
    "message_template": {
      "status": "known",
      "value": {
        "pair_count": 2,
        "pairs": [
          {
            "index": 0,
            "key_raw_hex": "...",
            "value_raw_hex": "...",
            "key": {"status": "known", "value": "..."},
            "value": {"status": "known", "value": "..."}
          },
          {
            "index": 1,
            "key_raw_hex": "...",
            "value_raw_hex": "...",
            "key": {"status": "known", "value": "..."},
            "value": {"status": "unknown", "reason": "BATTLE_TEXT_DECODE_FAILED"}
          }
        ],
        "basis": "copied_native_message_template_inputs",
        "full_display_complete": false,
        "runtime_popup_verified": false
      }
    }
  }
}
```

v4 帧没有 `BTXT` 扩展时，投影状态是 `unknown`，不是“已知空模板”。截断、版本错误、长度不一致、尾随字节和不符合上限的键值都会拒绝该帧。v2/v3 解码仍按原有兼容路径处理；旧版本没有模板输入时报告 `unsupported`，不会伪造 v4 结果。

这些状态还会明确写在事件完整性字段中：`full_display_complete`、`runtime_popup_verified`、`native_visibility_verified` 和 `business_complete` 当前均不能因为拿到了键值就变成 `true`。`event_id` 仍然是采集记录的身份，不是稳定的游戏战斗 ID；同一战斗的去重和最终业务语义尚未由这条路径证明。

## 采集和公开流程

1. 自然入口先为一个路由记录建立一次 scope 保留。路由器把待关联的基础记录放入 FIFO 队列；消息包装器只接受与该记录匹配的 land/naval 返回地址、回调拥有者、kind 和日期。重复基础记录、重复消息、未知返回地址、错误回调、错误 formatter owner/caller、日期或 kind 不匹配、缺失 scope 和溢出都会拒绝关联。
2. scope 通过后，原始消息模板复制到自有缓冲区。复制阶段只保存有限字节和标量，不保存游戏指针；随后用两遍读取比较头部、节点链、字符串和附加字段。键值顺序与重复键原样保留，字符串按长度和终止条件校验。
3. wire 解码器先验证完整的 v3 基础帧，再验证可选的 `BTXT` 扩展。解码器只接受一个完整帧，不能递归嵌套 v4，也不能用缺失扩展推断空结果。
4. `project_template` 对日期做一致性检查，并对每个键和值分别执行 `eu4_escape` 解码。`battles.py` 将结果放入 `details.message_template`，同时保留原始结果数值、原始标志和记录顺序。
5. `LiveBattleIngestor.refresh()` 只对已装组件产生的本地 checked JSONL 做有界增量摄取，推进已有 tail、传输和重组游标，再写入指定 SQLite。它不启停游戏、不调用原生查询、不连接网络，也不扫描全量归档。重启后根据持久游标继续读取，重复帧按既有传输/重组合同处理。

## scope 和入口安全边界

固定 PE/REA 证据把路由入口、消息入口和共享回调作为三类关联目标：路由入口 RVA `0x23A020`，消息入口 RVA `0x244630`，共享回调静态目标 VA `0x1402EC0A0`。消息的两个直接 formatter 返回锚点分别是陆战 RVA `0x236721` 和海战 RVA `0x232A13`；它们用于把 FIFO 中的基础记录与恰当的消息调用配对。上述地址是静态/夹具合同，不能单独证明真实游戏窗口已经出现。

入口夹具记录了原始 RBP、调用者相关的保存 RDI 和精确返回地址锚点。自有 RX 区域在发布后保持进程生命周期，原函数通过尾跳只执行一次；shim 不调用原函数的副本。ABI 夹具还验证了 RFLAGS、易失 GPR、XMM0–5 的 128 位内容、MXCSR、x87 控制字、GetLastError、返回地址和栈参数的保持，以及回调前后 Win64 对齐。展开信息按入口、完整栈帧、恢复 flags、尾跳四个自然边界覆盖，不能把 `popfq` 前后的指令误当作普通 epilog。嵌套回调只在自有夹具中验证，尚未证明生产队列的重入保护。

## 读取上限和失败含义

以下上限是防止读取失控的工程边界，不是 EU4 游戏数据或消息长度的最大值：

| 项目 | 上限 |
| --- | ---: |
| 单个 v4 wire 帧 | 256 KiB |
| v3 基础帧 | 64 KiB |
| 键值对数量 | 128 |
| 单个键 | 128 B |
| 单个值 | 8192 B |
| 辅助字符串 | 8192 B |
| 键值与辅助字符串 arena | 64 KiB |
| 单遍 native 读取 | 128 KiB |
| 两遍累计读取 | 256 KiB |

节点链未终止、循环、指针或字符串不合法、两遍结果变化、输出与输入重叠、预算超限和读取失败都会返回失败或 `unknown`，不会截断后发布一个看似完整的值。固定上限不意味着游戏中不存在更长的内容；超限内容必须由后续明确扩展合同处理。

## 目前仍未闭合的内容

模板键值复制尚未证明完整的控件树、窗口标题、最终正文、换行和 UI 条件。RVA `0x23A930` 的静态证据只闭合了 NAME 标题输入，不能当作完整标题或描述来源。`full_display_complete` 和 `runtime_popup_verified` 继续保持 `false`；动态 `$`、`[]` 或其他游戏语义也不会由本层擅自求值。歼灭、撤退等战斗字段仍缺少独立来源，不能从 flag、剩余兵力或胜负结果推断。

当前路径也没有证明观察者的完整可见范围、稳定 war/battle ID、双方业务角色、原生消息窗口实际显示或 LLM 已读。消费者读取失败时应重读同一条原始记录，而不是重新触发游戏入口；传输层的重复帧也必须按记录身份去重，不能把重试当成新战斗。

`checkpoint-v26-001/outcome-001.json` 记录了保留进度的保存：名称为 `llm_diplomacy_information_v26_checkpoint_20261026_001.eu4`，结果日期 raw `56556048`，保存文件 SHA-256 为 `109a2b7a32a06204caa080edf1c7ba27f84e3aef3d8127c5105e42343de18143`。该结果的会话仍对应此前 v25 安装，因此这里只把它作为进度保留和来源追溯记录，不把它当作 v26-003 的安装、实机窗口或 v4 验收。

本批真实窗口已经执行并关闭，但没有捕获到可用模板扩展。下一次采集仍需分别记录实际 PID/创建时间、DLL 与 manifest 身份、日期前后状态、scope 配对、完整模板字节和公开投影；在这些事实闭合前，不能把 absent 结果、合成测试或静态候选写成完整战报。
